Documentation

  • lang

    Primitives of Vun.

  • lang.abi

    Calling conventions (spec 07, section 4).

  • lang.arch

    The instruction sets a block of instructions is written in, each a namespace declaring its table (spec 07, section 6): x86_64, arm64, thumb and wasm32; and what a block is written with, whatever its instruction set.

  • lang.arch.arm64

    64-bit ARM (spec 07, section 6): its registers, and each instruction with its forms as the toolchain's assembler encodes them (Arm A64 ISA), with what each form reads and writes. The instructions are declared in control, fp, int and memory, what their operand positions take in operand; vun-isa-arm64's tables are generated from these declarations. An alias is an instruction of its own, its fixed fields in its base word: mov is orr from the zero register, cmp is subs into it.

  • lang.arch.arm64.control

    Branches, calls, traps, barriers and page addresses (Arm A64 ISA, branches, exception generation and system instructions).

  • lang.arch.arm64.fp

    Scalar floating-point instructions (Arm A64 ISA, scalar floating-point data processing): the instruction's width is the precision, or for a conversion the integer's width.

  • lang.arch.arm64.int

    Integer moves, arithmetic, logic, shifts, extensions and conditional selects (Arm A64 ISA, data processing).

  • lang.arch.arm64.memory

    Loads, stores and atomics (Arm A64 ISA, loads and stores). A single access has a form per addressing mode, tried in order: a scaled offset, an unscaled one (ldur), a register index, pre- and post-index, then the low bits of a symbol's address.

  • lang.arch.arm64.operand

    What an operand position of an arm64 form takes, and how its operand is encoded: registers by width, immediates, addressing modes, conditions and branch targets.

  • lang.arch.thumb

    Thumb, the instruction set of Arm's M profile and of Arm's A profile in its Thumb state (spec 07, section 6): its registers, and each instruction with its forms as the toolchain's assembler encodes them (Armv7-M, Thumb-2 with the floating-point extension), with what each form reads and writes. The instructions are declared in branch, data, fp, memory, multiply and system, what their operand positions take in operand; vun-isa-thumb's tables are generated from these declarations.

  • lang.arch.thumb.branch

    Branches, calls, returns and traps (Armv7-M, branches and exception-generating instructions).

  • lang.arch.thumb.data

    Moves, arithmetic, logic, shifts, comparisons, extensions and bit operations (Armv7-M, data processing). A family's members differ in the operation's four bits at 21 and the flags' bit at 20.

  • lang.arch.thumb.fp

    The floating-point extension: arithmetic, comparisons, moves, loads and stores, and conversions, single precision and double (Armv7-M FPv5, the encodings of VFPv4). Where a form is defined at both precisions, its double-precision one sets bit 8 (sz).

  • lang.arch.thumb.memory

    Loads and stores, of pairs, of lists of registers and exclusive ones (Armv7-M, load and store). Each access width has its own encodings, so each is an instruction of its own.

  • lang.arch.thumb.multiply

    Multiplication, with accumulation and 64-bit products, and division (Armv7-M, multiply and divide).

  • lang.arch.thumb.operand

    What an operand position of a Thumb form takes, and how its operand is encoded: registers, immediates, addressing modes, lists, branch targets and conditions.

  • lang.arch.thumb.system

    The special registers, interrupt masks, waits and barriers (Armv7-M, system instructions).

  • lang.arch.wasm32

    WebAssembly 32-bit, the instruction set of the wasm32 targets (spec 07, section 6): the instructions of its stack machine with what each pops and pushes, as the toolchain's backend encodes them. They are declared in arithmetic, compare, control, convert, local and memory; vun-isa-wasm32's tables are generated from these declarations.

  • lang.arch.wasm32.arithmetic

    Arithmetic on integers and floats, each popping its operands (the last on top) and pushing its result.

  • lang.arch.wasm32.compare

    Comparisons: each pops its operands (the last on top) and pushes 1 or 0 as an i32.

  • lang.arch.wasm32.control

    What stops the code, or does nothing.

  • lang.arch.wasm32.convert

    Conversions between integer and float types, and extensions of narrow integers.

  • lang.arch.wasm32.local

    Locals and the stack.

  • lang.arch.wasm32.memory

    Loads and stores, and the size of memory. An access takes its address on the stack and two immediates: the alignment as a power of two, and an offset added to the address.

  • lang.arch.x86_64

    x86-64 (spec 07, section 6): its registers, and each instruction with its forms as the toolchain's assembler encodes them (Intel SDM volume 2), with what each form reads and writes. The instructions are declared in arith, control, int and sse; vun-isa-x86_64's tables are generated from these declarations, so the language, the assembler and its listings share one table. names holds what a block of instructions is written with.

  • lang.arch.x86_64.arith

    Integer arithmetic, logic, comparisons and shifts; each writes the flags.

  • lang.arch.x86_64.control

    Conditions, jumps, calls, the stack, and atomic and string operations.

  • lang.arch.x86_64.int

    Integer moves and arithmetic.

  • lang.arch.x86_64.sse

    SSE instructions: moves between general and SSE registers, scalar float arithmetic, comparisons and conversions. Each has its mandatory prefix before REX, then 0F and its opcode.

  • lang.bounds

    What bounds hold (spec 04): the iterator of lang.Bounds in lang.ops reads them.

  • lang.check

    Checks of unsafe code at run time (spec 07, section 7; spec 13, section 8.7): what a program may be built to check, the operations its runtime provides for the checks, and how a failed one is reported.

  • lang.check.mem

    The operations of lang.mem on raw pointers, checked (#[check.by(.pointers, f)]): each checks the bytes it touches, then does what it checks.

  • lang.comptime

    Compile-time evaluation budgets (spec 03, section 7).

  • lang.cover

    Coverage (spec 11, section 6): a program built covered, as vun fuzz builds one, sets the flag of each block of its code in map as the block starts, the flag of the block's number modulo size. std.testing.fuzz reads the flags to tell inputs apart by what they ran.

  • lang.diag

    Diagnostics as values (spec 10).

  • lang.errors

    Every compiler diagnostic, grouped by area. cargo gen derives the ids of vun-diag from this file. Each entry's explanation page is the file its binding path names, errors/<group>/<name>.md (spec 10, section 1).

  • lang.float

    Floating-point operations that are explicit about precision (spec 04, section 2).

  • lang.float.ops

    Floats' operators (spec 02, section 4): the impls of lang.ops for every float type, over the constructor lang.Float, as the primitives of lang.float.

  • lang.float.soft

    Float operations no instruction computes, written with those that do (spec 13, section 3): each takes its operands' encodings apart through lang.float.bits, computes on integers, and assembles the result as IEEE 754 gives it. lang.float.rem and mul_add run as these.

  • lang.float.soft.arith

    IEEE 754 arithmetic written with integers, for a processor computing no float of the type (lang.lower.soft): each operand taken apart through lang.float.bits, the result exact in integers twice as wide as the float, then rounded once to nearest, ties to even; a NaN result is the canonical NaN, as the instructions' are made (spec 04, section 2).

  • lang.float.soft.compare

    IEEE 754 comparisons written with integers, for a processor computing no float of the type (lang.lower.soft): a NaN is equal to nothing and in no order, zeros of both signs are equal, and other floats are in the order of their signed magnitudes.

  • lang.float.soft.convert

    Conversions written with integers, for a processor that does not convert between the types (lang.lower.soft): a float it lacks, or an integer wider than an address. Each takes the encoding apart through lang.float.bits and rounds once, to nearest, ties to even, as the primitives of lang.float say.

  • lang.flow

    Guaranteed tail calls (spec 09, section 3).

  • lang.hint

    Hints inside function bodies (spec 09, section 3).

  • lang.int

    Integer types by width (spec 04, section 1). lang declares them, since its own declarations need them; std.prelude re-exports them.

  • lang.int.ops

    Integers' operators (spec 04): every operator on integers is a call of its lang.ops interface's function, which these impls give as the primitives of lang.int (spec 02, section 4). Each takes the right operand's range per call, so a result's range is computed from both operands' (rule 1), and bit operations keep a uN type (rule 8).

  • lang.kind

    Kind restrictions (spec 05, section 1).

  • lang.layout

    Layout attributes (spec 05, section 6).

  • lang.link

    Linking attributes (spec 08).

  • lang.lint

    Lints as values (spec 10, section 4). A lint states its group, its default level and a check for each kind of node it looks at; the compiler walks the typed code once per file and runs each check a lint states on each node of its kind, at compile time. A check sees the code through Cx and the nodes as plain data, a view versioned with lang, and reports by appending to Cx: running it is a pure compile-time call.

  • lang.lower

    How the compiler lowers what no instruction computes (spec 13, section 3).

  • lang.mem

    Borrows, raw pointers and memory access (spec 05).

  • lang.mem.soft

    Atomic accesses of integers wider than an address, for a processor whose atomic instructions reach one word (lang.lower.soft): on Thumb, where Arm's A profile has exclusive loads and stores of two words (lang.arch.thumb.Feature.application), loops of them between barriers, as the word's are made, which makes each sequentially consistent whatever order it asks. No other processor has one written yet, and reaching one there is an error while compiling.

  • lang.meta

    Code values, names, reflection and origins (spec 03).

  • lang.ops

    Operators as interfaces. Every operator desugars to one of these (spec 02, section 4); the table operators of lang.syntax.desugar says which.

  • lang.opt

    Optimization controls; none changes meaning (spec 09, section 3).

  • lang.panic

    Traps and the typed link symbol that handles them (spec 07, section 3; spec 08).

  • lang.safety

    What unsafe marks (spec 07, section 4): something used only where someone vouched for the facts the compiler cannot check. A block or expression is vouched for where it is written; a function, or a function type, at each call.

  • lang.scope

    Where a restricted name is visible (spec 01, section 7): the argument of lang.visible.

  • lang.simd

    Vector types (spec 04, section 3): lanes values of one type, operated on together. A vector is laid out as the array of its lanes, aligned to its size when that is a power of two; lanes and of move between the two, over which std.simd gives vectors their operators and methods.

  • lang.stack

    Stack bounds (spec 07, section 4).

  • lang.syntax

    The syntax of Vun as types, for compile-time code reading code values (spec 03, section 4). Token and node types are generated from syntax/grammar.vun.

  • lang.syntax.desugar

    What syntax means (appendix B): the lang items operators, borrows and other forms desugar into, as data the compiler looks up, so no lang name is written in the compiler. Read with grammar.vun, whose token kinds these tables name. A table naming lang items by their paths is a tuple, since the items it names have types of their own.

  • lang.syntax.editors

    How editors show and navigate Vun, beside its grammar (spec 13, section 5): what the tree-sitter queries capture and the Sublime syntax scopes. cargo gen reads it with grammar.vun and nodes.vun; captures and scopes are named as the generator declares them, and each editor names a capture its own way.

  • lang.syntax.grammar

    The grammar of Vun, defined once with nodes.vun, which holds the kinds of nodes and their productions, and tables.vun, the tables that say how they nest: its tokens and tables. Generates the Rust vun-grammar crate, lang.syntax, the formatter's tables and the editor grammars (spec 13, section 5).

  • lang.syntax.nodes

    The kinds of syntax tree nodes and their productions, part of the grammar with grammar.vun, whose header says how both are read.

  • lang.syntax.tables

    The tables that say how kinds nest and are told apart, part of the grammar with grammar.vun and nodes.vun, whose productions name them (the header of grammar.vun says how all are read).

  • lang.target

    Target descriptions and feature requirements.

  • lang.thread

    Storage per thread (spec 07, section 2).

  • lang.trace

    What the compiler tells a program of its own code, so that a trap reports where it was written and the calls that led to it (spec 07, section 3): the program's functions, its trap sites and the places in source they name. The compiler lays the table out as these declarations do and gives it the link symbol symbols.table, which a runtime declares to read it.

  • std

    The standard library: ordinary code over lang, holding no privilege user code lacks.

  • std.build

    The build API used by build.vun files (spec 12, section 2). build runs at compile time, in the sandbox, with a &mut Build capability, and records a plan: steps that the driver carries out once it returns. What only the package knows, its dependencies' names and parameters, a program's options, is written as records, which the driver reads by reflection (decision 116).

  • std.check

    Shadow memory for the checks of unsafe code at run time (spec 07, section 7; spec 13, section 8.7): one byte for each granule bytes of the address space, 0 where all of them may be accessed, k where the first k may, and a negative code saying why where none may. The shadow of each span of 1 << span_bits addresses is reserved the first time memory in it is described, so it follows the program's memory wherever the system puts it. A runtime gives how memory is mapped (mapped) and exports the operations of lang.check over the state (exports). The state is read and written by atomic accesses, which no check rewrites.

  • std.check.quarantine

    Memory given back to allocators, held poisoned before they may hand it out again (spec 13, section 8.7): a ring of what was given back, oldest first. Past lang.check.quarantine bytes, each free gives back the oldest memory of the allocator freeing, so memory leaves only for an allocator known to be alive.

  • std.check.stack

    The checks of the stack (spec 13, section 8.7): the export of a runtime that checks the frames of its stack and nothing else, over the bounds it knows.

  • std.check.table

    What allocators have handed out, for the checks of allocations (spec 13, section 8.7): the bytes handed out at each address, open-addressed by linear probing. A removal moves later entries of its run back rather than leaving a tombstone, so probes stay as short as the table is full.

  • std.check.words

    Words of memory a runtime gives the checks, read and written by atomic accesses, which no check rewrites.

  • std.cmp

    Comparing values through lang.ops.PartialOrd, whose < and > these use.

  • std.cmp.tests

    Tests of std.cmp and of the equality types derive from their parts (lang.ops.Eq).

  • std.codec

    Codecs: bytes as text in the encodings of RFC 4648 (Base: hex, base32, base64) and as variable-length integers (varint). Encoders write to any std.fmt.Writer and decoders write the bytes to one, so none of them needs an allocator. Checksums are std.hash.crc32 and std.hash.adler32.

  • std.codec.base

    Encodings that cut bytes into groups of 4, 5 or 6 bits (RFC 4648), each group a symbol of an alphabet that is a power of two long. The three are one rule with a table: the group size, the alphabet, whether a block of symbols is padded to its full size, and whether letters of either case decode.

  • std.codec.tests

    Tests of std.codec: the vectors of RFC 4648, strictness of decoding, varints.

  • std.codec.varint

    Variable-length integers (LEB128): seven bits of the number to a byte, least significant first, the high bit of a byte set when another follows. A signed number goes by its zigzag, which keeps small magnitudes short.

  • std.collections

    Collections: Vec, a growable array over an allocator the caller passes, struct-of-arrays layouts generated by reflection, and Handle(T), typed indices into a pool over nominal structs (decision 41, spec 05, section 4).

  • std.collections.map

    HashMap(K, V): values by key, in open addressing over one buffer an allocator gave: the states of the slots, then the keys, then the values. Keys are compared by Eq and hashed by std.hash.Hash, both derived for the types made of ones that have them. It is linear, as Vec is, and holds no allocator: the one passed to a call that grows it is the one deinit must be given. Keys and values are not dropped: ones owning memory are taken out first.

  • std.collections.tests

    Tests of std.collections.

  • std.collections.vec

    Vec(T): items of one type in a buffer an allocator gave, grown as they are pushed. It is linear: it owns its buffer, which deinit gives back to the allocator it came from, the one each growing call is passed. No allocator is held, so one allocator serves any number of them.

  • std.diag

    Diagnostics from compile-time code (spec 10, section 3).

  • std.float

    Float methods (spec 04, section 2): conversions, an impl for every float type over the primitives of lang.float.

  • std.fmt

    Formatting, with format strings read at compile time (spec 03, section 4): print(w, "{} args\n", n) writes the text of the format string with each {} replaced by the next argument, as its Format impl writes it. Another specifier between the braces writes it another way: {?} by Debug, {x} by Hex and {b} by Binary. After a : goes where it sits in a width: {:>8} pads on the left to 8 bytes, {x:0>4} with 0, {:^5} on both sides.

  • std.fmt.debug

    Debug output, {?} in a format string: a value written as the expression that builds it, for a reader of the program. An integer is its digits, a bool true or false, bytes a quoted string, other items [a, b], a tuple (a, b), a variant .name or .name(a, b) and a struct Name{ .field = a, .other = b }, as the compiler shows values. A struct or an enum whose parts have Debug has it without an impl, by derive_debug.

  • std.fmt.json

    JSON (RFC 8259) written from typed values, each type writing itself through Json: an integer is a number, a float a string of its exact hexadecimal form, a bool true or false, bytes a string, another sequence an array and an option its value or null. derive(T) writes a struct or a record as an object of its fields, a tuple as an array of its items, and an enum's value as its variant's name, or, where the variant holds parts, as an object naming it; a type of these without a Json of its own is written as derive(T) writes it.

  • std.fmt.layout

    The layout of an argument in a format string (spec 03, section 4): after a : in its place, an optional fill and alignment, <, > or ^, and a width, as in {x:0>8} or {:^5}. An argument shorter than the width is padded with the fill; a longer one is written whole.

  • std.fmt.places

    The places of arguments in a format string (spec 03, section 4): {}, {?}, {x} and {b}, each a row of specs, then optionally a : and a layout (fmt/layout.vun), read once at compile time into the text between them, or the first problem.

  • std.fmt.tests

    Tests of std.fmt: the places of arguments in a format string, and debug output.

  • std.hash

    Hashing: a value feeds its parts to a Hasher, which answers a u64. Values that are equal (lang.ops.Eq) hash equal. A struct or an enum whose parts can be hashed can be hashed without an impl, by derive_hash; Fnv is a hasher for tables.

  • std.hash.adler32

    Adler-32 (zlib's checksum): two sums modulo 65521, of the bytes and of the first sum after each byte. Faster than a CRC and weaker on short inputs.

  • std.hash.crc32

    CRC-32 (the checksum of Ethernet, zlib and PNG): the remainder of the bytes as a polynomial, reflected, with the polynomial 0xEDB88320. It is a checksum against accidents, not a hash against an adversary.

  • std.hash.tests

    Tests of std.hash: equal values hash equal, different ones almost never do, and types hash by their parts without an impl.

  • std.hw

    Hardware access: memory-mapped registers over volatile operations.

  • std.int

    Integer methods (spec 04, section 3): narrowing to another integer type, an impl for every Int(r) over the primitives of lang.int.

  • std.int.bits

    Integers as the bits of their storage (spec 04, rule 8): rotating them and counting them. A signed value is its two's complement, so every Int(r) is rotated and counted by its word.

  • std.int.bytes

    Integers as the bytes of their storage (spec 04, rule 7): to_le and to_be give the bytes of a value, from_le and from_be read a value from them. A signed value is its two's complement, so every Int(r) is read and written alike.

  • std.int.tests

    Tests of std.int: integers read from text.

  • std.io

    Moving bytes: Reader, where bytes come from, and Writer (std.fmt.Writer), where they go; a reader over a borrowed slice. Streams of the system are readers and writers (std.os.Stream), and so are the buffers of std.text.

  • std.io.tests

    Tests of std.io: a reader of a slice.

  • std.iter

    Iteration is suspension (spec 06, section 3): an iterator is a coroutine yielding its items, and adapters are coroutine functions over one, methods of every frame.

  • std.lints

    The standard lints, grouped (spec 10, section 4): each group is a namespace, which configuring names, as std.lints.pedantic, and which declares its default level.

  • std.lints.correctness

    Code that is wrong or useless.

  • std.lints.layout

    Organization of namespaces, files and directories (spec 10, section 5).

  • std.lints.naming

    Naming conventions: case follows what a binding is (spec 10, section 5).

  • std.lints.nursery

    New lints, still being tuned.

  • std.lints.pedantic

    Strict checks, with the occasional false positive.

  • std.lints.perf

    Performance lints: padding, large copies, wide intermediates.

  • std.lints.restriction

    Restrictions a project chooses, such as no unsafe.

  • std.lints.style

    Code that is written in an unusual way.

  • std.lints.suspicious

    Code that is most likely wrong.

  • std.log

    Deferred logging: format strings interned in a non-loaded section (spec 12, section 9).

  • std.mem

    Memory: allocators, owning pointers, copying, and Arena, which hands out &mut T tied to the arena borrow so that trees are ordinary scoped values (decision 40, spec 05, section 4).

  • std.mem.alloc

    Allocators are capabilities (spec 07, section 1).

  • std.meta

    Reflection and code generation helpers over lang.meta (spec 03), including collect(package, attr), which gathers declarations carrying an attribute (decision 42).

  • std.option

    Options: methods of every ?T, by an impl without an interface.

  • std.os

    Hosted runtimes and the System capability (spec 08, section 2). A hosted program is start := std.os.start(main); the runtime makes the one System and passes it to main.

  • std.os.file

    Files a hosted program opens through its std.os.System (spec 08, section 2).

  • std.os.libc

    A runtime on top of the C library: exports C main, the trap handler, the critical section and the executors' sleep, and reaches the system through the C library's functions (spec 08, section 2).

  • std.os.libc.library

    Loading libraries through the C library (dlopen, dlsym, dlclose): the exports a runtime on top of it holds, library := std.os.libc.library.exports. The loader reports a failure as text rather than an error number, so each is unresolved.

  • std.os.libc.pages

    std.os.pages's exports for a runtime on top of the C library: mprotect, and a query of /proc/self/maps where the system is Linux's, which gives a process no other way to its own.

  • std.os.library

    Libraries a hosted program loads as it runs (spec 08, section 2): shared objects the system finds by path or name, whose functions the program calls once it has their addresses. The system names a library by a number, as it does a file.

  • std.os.linux

    Linux.

  • std.os.linux.kernel

    A runtime calling the kernel itself, for static programs without a C library (spec 08, section 2). _start finds the arguments where the kernel puts them, on the stack it starts the process with, and every request is a system call. The C compiler may call the four functions of C's string.h a freestanding program must provide, so the runtime exports them.

  • std.os.linux.kernel.calls

    The numbers of the system calls the kernel runtime makes, which each architecture assigns its own.

  • std.os.linux.kernel.division

    The hooks the Arm EABI's division functions call for a divisor of zero (__aeabi_idiv0, __aeabi_ldiv0), which the platform may supply. A C compiler for 32-bit Arm divides through functions of its own library, and GCC's Linux one answers a zero divisor through the C library's raise; a program without one supplies the hooks itself. Vun checks its divisors, so reaching a hook is a trap.

  • std.os.linux.kernel.pages

    std.os.pages's exports for the kernel runtime: mprotect by raw system call, and a query of /proc/self/maps, which std.os.linux.pages reads needing no system call of its own.

  • std.os.linux.kernel.thread

    Threads of a program calling the kernel itself. Each runs on a stack of its own, mapped for it with its lowest pages left inaccessible so that running past its end faults, and starts from clone, sharing the process's memory, files and signal handlers. The kernel clears the thread's id in its record when the thread ends and wakes whoever waits on that word (CLONE_CHILD_CLEARTID): joining waits for it, then unmaps the stack.

  • std.os.linux.kernel.tls

    Storage per thread of a program calling the kernel itself (spec 07, section 2). The program's TLS segment, which the auxiliary vector the kernel starts it with leads to, is the image each thread's block starts as; a block is laid out as the architecture's ABI says, and the thread pointer, which code reaches the block from, is set to it for each thread.

  • std.os.linux.pages

    Pages as Linux's mprotect takes them, and as /proc/self/maps describes them: a line per mapped range, its ends in hex and rwxp for what it allows, before whatever else it holds.

  • std.os.macos

    macOS.

  • std.os.memory

    The functions of C's string.h a freestanding C program must provide, which a C compiler calls for copies and fills of its own: a runtime with no C library holds them. Copies and fills are written in assembly: a loop in Vun would be read back by the C compiler as a call of the function it is.

  • std.os.pages

    The pages of the process's own address space (spec 08, section 2): what a range of them allows, and the range an address is mapped within. An address passed here must be one the system gave the process: through a library it loaded, its own code and data, or memory it mapped.

  • std.os.thread

    Threads the system runs beside the one starting them (spec 08, section 2). A thread runs a closure borrowed for as long as it runs: Thread is linear and holds the borrow, so the closure, and what it borrows, stay until the thread is joined, and joining gives what the closure returned. Values safe to share are safe to share across threads (spec 07, section 2), so a closure may borrow what the thread starting it goes on reading.

  • std.os.wasi

    WASI preview 1 (spec 08, section 2): a runtime exporting _start, which reaches the system through the functions of preview 1's import module. A module runs one thread and takes no signals, so its critical section is nothing to take.

  • std.os.wasi.stack

    The stack of a WASI program, in the linear memory the linker lays out.

  • std.os.windows

    Windows (spec 08, section 2): a runtime calling kernel32 itself, with no C runtime, for programs that run one thread. A file number is a handle (file), the command line is split into arguments by the C runtime's rules (command_line), and the system's errors are the ones std.os.Error names, or its own number.

  • std.os.windows.clock

    The system's clocks and sleep, in the units std.time keeps.

  • std.os.windows.command_line

    The command line of a Windows process: one string of UTF-16, which a program splits into its arguments itself. The rules are the C runtime's, as Microsoft documents them:

  • std.os.windows.file

    Files as the system hands them out: handles, which a std.os file number stands for, the modes std.os.file.Mode asks for in the system's words, and paths in UTF-16.

  • std.os.windows.kernel32

    The functions of kernel32 the runtime calls, each by its link symbol (spec 08, section 3): the system's own, which a program of this runtime links by name and no C runtime stands between. They are stdcall, the system's convention on 32-bit x86, which x86-64 takes for its one. A handle is a usize, a BOOL an i32, a DWORD a u32.

  • std.os.windows.library

    Loading libraries through kernel32: the exports a runtime holds, library := std.os.windows.library.exports. A module's number is its handle, the address it is loaded at; the loader reports a failure as an error number, which none here is told apart by, so each is unresolved.

  • std.os.windows.pages

    Pages as VirtualProtect and VirtualQuery take and give them: PAGE_*'s eight kinds of access, and the fields of MEMORY_BASIC_INFORMATION past AllocationBase, which a pointer's width places: AllocationProtect is padded to keep RegionSize a pointer's width aligned, so the longest a pointer is wide places every field from it on.

  • std.os.windows.stack

    The stack probe a Windows program provides. Windows commits a thread's stack a page at a time, as the thread touches the guard page below what it has committed, so a function with a frame of more than a page touches each page of it in order first: it calls __chkstk with the size of its frame in rax, and the call leaves every register but r10, r11 and the flags as they were. The frame itself is taken by the caller after it.

  • std.os.windows.tests

    Tests of std.os.windows: a command line split into the arguments a program is given, and a clock before the epoch.

  • std.panic

    Ending the execution context (spec 07, section 3): fail is a trap site with a message.

  • std.prelude

    Names every file sees without qualification, unless its manifest lists another prelude (.prelude, spec 01, section 8).

  • std.ptr

    Raw pointers (spec 05, section 5): methods of every *T over the primitives of lang.mem. Creating a pointer and reading its address are safe; the rest is unsafe to call, and each body vouches for the primitive it calls.

  • std.rand

    Random numbers: an Rng answers a u64 each time it is asked and holds its state, so a seed fixes everything it gives. These generators are not for secrets. The default methods draw bounded numbers, bytes and shuffles from next, whichever generator gives it.

  • std.rand.pcg

    PCG-XSH-RR 64/32: a 64-bit linear congruential state, whose output is 32 bits xored, shifted and rotated. A stream picks one of 2^63 sequences, so two generators on one seed can differ.

  • std.rand.splitmix

    SplitMix64: the state steps by a constant and is mixed on the way out. Every seed is good, and the same seed gives the same numbers on every target.

  • std.rand.tests

    Tests of std.rand: the reference outputs of each generator, and what every Rng guarantees.

  • std.rand.xoshiro

    xoshiro256**: four words of state, a period of 2^256 - 1. The state must not be all zero, so a seed is spread over it by SplitMix64, which never gives four zeros.

  • std.re

    Tools for reading binaries, which a program of its own builds on: byte patterns with wildcards (Pattern), as a reverse engineer writes them, and a hex dump of bytes (hexdump).

  • std.re.dump

    The hex dump std.re.hexdump writes: the bytes of a run, a line of 16 at a time.

  • std.re.pattern

    Byte patterns as a reverse engineer writes them: hexadecimal bytes separated by spaces, with ? or ?? for a byte that may be any, as in 48 8B ?? 05.

  • std.re.tests

    Tests of std.re: patterns with wildcards found in bytes, and hex dumps.

  • std.result

    Results (spec 07, section 3): methods of every Result(T, E), by an impl without an interface.

  • std.seq

    Arrays and slices (spec 05): what every [n]T and [T] answers, by impls for lang.mem.Array and lang.mem.Slice over the primitives of lang.mem.

  • std.seq.search

    Looking in a slice and cutting it (spec 05): methods of every [T], and so of every [n]T, whose items have ==, text among them, by an impl without an interface.

  • std.seq.sort

    Ordering a slice in place (spec 05): methods of every [T], and so of every [n]T, with no allocator. Short runs are insertion sorted; longer ones are heap sorted, so no input is slow. The sort is not stable: items that are equal may change places.

  • std.seq.tests

    Tests of std.seq: looking in a slice and cutting it.

  • std.simd

    Portable vector code (spec 04, section 3): the methods and operators of every lang.simd.Vector(n, T), lane by lane over the array of its lanes. An operator's lanes have the type the same operator gives their lanes (u8 lanes sum to Int(0..=510) lanes).

  • std.sync

    Synchronized interior mutability; the only safe kind (spec 07, section 2). A critical section is global mutual exclusion: Shared(T) is reached only with the &Critical it lends, and Atomic(T) and Mutex(T) synchronize by themselves.

  • std.task

    Asynchronous tasks and executors (spec 06). A task yields Wait requests; the executor, not the task, owns wakeups. Executors are library code over frames: run for bare metal, block_on for one task on a hosted system, select inside a task.

  • std.testing

    Tests, properties, benchmarks and simulation (spec 11). The runner is an ordinary program: start := std.testing.runner(app); runs every test of the namespace app and those nested in it, each on a thread of its own, since a trap ends only its thread (spec 07, section 3), and writes one JSON line per test, then one of the totals (spec 11, section 3). A test whose one parameter is &mut Bench is a benchmark (std.testing.bench), one whose one parameter is &mut Sim a simulation (std.testing.sim); a test with other parameters is a property, run with arguments generated from their types (std.testing.property), as a simulation runs with its schedules drawn from the same choices.

  • std.testing.bench

    Benchmarks (spec 11, section 5): a test whose one parameter is &mut std.testing.Bench. Run as a test, its loop runs the body once; measured (vun bench), the loop runs the body in batches, each as many times as all before it, until it has run least nanoseconds, and the benchmark reports how many times the body ran and how long that took. The clock is read between batches only, and the body never sees how many times it runs.

  • std.testing.fuzz

    Coverage-guided fuzzing (spec 11, section 2): vun fuzz builds the tests covered (spec 11, section 6) and runs each property, fuzz target and simulation over as many cases as --fuzz asks. A case replays the choices of a stream kept, mutated, then draws; or draws new ones. It is kept in turn when it set a flag of lang.cover.map no case before set, so the streams kept reach ever more of the code. A case that traps is shrunk and reported as a property's is.

  • std.testing.options

    How a run of the tests' program is asked for: the options its arguments give (spec 11, section 3).

  • std.testing.property

    Property tests (spec 11, section 2): a test's arguments are generated from its parameters' types, each read from a stream of choices, so the case that fails is replayed and shrunk as its choices, whatever generated it. A parameter whose type borrows, such as &[u8], is lent what the case holds for it (lend).

  • std.testing.property.lend

    How a property's case passes an argument of a type that borrows what it reaches (spec 11, section 2): it holds a value generated as any other, and lends it.

  • std.testing.property.shrink

    Shrinking a failing case (spec 11, section 2): on the choices it took, whatever generated them, towards fewer and smaller ones.

  • std.testing.sim

    Deterministic simulation (spec 11, section 4): a test whose one parameter is &mut Sim runs tasks, std.task.Async frames, on a virtual clock, one at a time, each next one chosen among those ready by the case's choices. They are the choices a property's arguments are read from, so a simulation runs over the cases a property does, a failing one is shrunk on its choices, and --seed replays it exactly. Time passes only when no task is ready: the clock jumps to the earliest time a task sleeps until.

  • std.text

    Text (decision 43): bytes held, written and cut. Slab(n) keeps up to n bytes inline, with no allocator; text is UTF-8 in &[u8], whose bytes ascii classifies and whose code points utf8 reads. Formatting is std.fmt, readers and writers are std.io, maps are std.collections.

  • std.text.ascii

    ASCII bytes (decision 43): which class a byte is of, its other case and the digit it writes. Bytes past 127 are in no class and stay as they are.

  • std.text.string

    String: bytes of text a program grows, in a buffer an allocator gave. Like Vec, which it holds, it is linear, and each call that grows it is passed the allocator, which deinit must be given back. Text is UTF-8 in &[u8]; a string keeps whatever bytes were put in it.

  • std.text.tests

    Tests of std.text: a slab written to as any writer, read back as bytes.

  • std.text.utf16

    UTF-16, as Windows spells text: units of 16 bits, a code point past U+FFFF written as a pair of surrogates. Text in a program is UTF-8 (decision 43); these read and write the units a system call takes, and turn one into the other.

  • std.text.utf8

    UTF-8 (decision 43): text is bytes, and these read and write the code points in them. A code point is a u32.

  • std.time

    Time as the system keeps it (spec 08, section 2): spans of time, and readings of the clocks a hosted program reaches through its std.os.System.

  • std.trace

    Backtraces (spec 07, section 3): where a trap was written and the calls that led to it, read from the program's table (lang.trace) and the chain of frames every function keeps, a record of its caller's frame and of where it returns to at its frame pointer. A runtime's handler of traps writes one before ending the program.
