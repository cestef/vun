# 12. Ecosystem: packages, project layout, tooling

Research notes, section 2, has the survey. The short version of what is copied and why:

| Copied | From | Because |
|--------|------|---------|
| content hash as package identity, URLs as mirrors | Zig, Nix, Roc | integrity without a central authority |
| minimal version selection, new major = new package | Go | deterministic, no solver, explainable |
| sorted line-per-entry integrity file | Go (`go.sum`) | conflict-free merges |
| toolchain pin with automatic download | Go, rustup | reproducible builds from a checkout |
| one unconfigurable formatter | gofmt, zig fmt | no style debates |
| API-computed version bumps | Elm, cargo-semver-checks | semver that means something |
| deferred logging | defmt | logs cost an index and packed bytes on the device |
| flashing and debugging as libraries | probe-rs, espflash | one CLI, no external runner |

| Avoided | Seen in | Because |
|---------|---------|---------|
| graph-wide additive features | Cargo | one dependent silently changes another's build |
| arbitrary code at build or fetch time | `build.rs`, dependencies' `build.zig` | unsandboxed, uncacheable |
| file-name conventions selecting code | Go `_linux.go`, Hare `+linux` | invisible selection |
| a single URL per dependency | Zig | a dead host breaks the build |
| a mandatory central registry | most ecosystems | governance burden, single point of failure |
| repackaging vendor SDKs | PlatformIO | lags vendors, forks the ecosystem |
| a bespoke data format | ZON | every tool needs a new parser |

## 1. Project layout

```
blinky/
  build.vun              manifest and build graph (section 2)
  lock.vun               generated, committed (section 4)
  blinky.vun             the package namespace: doc comment, re-exports, top-level declarations
  blinky/               its children (spec 01, section 8)
    app.vun              root file of the firmware program
    serial.vun
    serial/
      uart.vun
      _registers.vun     private to serial/
  tests/                integration tests: a test package that depends on this one
  tests/reject/         must-fail files with expected diagnostics
  tests/snapshots/      snapshot files
  examples/             one program per file, `vun build --example name`
  benches/              benchmark tests
  fuzz/                 corpus and crash inputs, per test
  docs/                 guides; API docs come from doc comments
  vendor/               only after `vun pkg vendor`
  .vun/               the toolchain's builds and saved queries, ignored by version control and never package content
```

No directory name is significant to the compiler except through `build.vun`, which states the roots.
The layout above is what `vun new` creates and what the `layout` lints expect.

## 2. The manifest is `build.vun`

`build.vun` is a Vun file conforming to the interface `std.build.Package`, which requires two
declarations: `package` and `build`. They are required by that interface, not by the compiler.

```vun
//! Blinky: an LED and a serial echo on an STM32F4.

package := .{
    .name = "blinky",
    .id = 0x6a80_91f5_7c7f_07ff,          // generated by `vun new`; survives renames
    .version = "0.3.1",
    .edition = 2026,
    .toolchain = "0.4.2",                 // exact; the launcher fetches it (section 6)
    .include = .{ "build.vun", "blinky.vun", "blinky", "LICENSE" },   // what the hash covers
    .prelude = .{ "std.prelude" },        // the default; `.{}` for none (spec 01, section 8)
    .deps = .{
        .stm32f4 = .{ .version = "1.3.0", .hash = "blake3:x7fa...",
                      .urls = .{ "https://git.example.org/stm32f4/1.3.0.tar.gz" } },
        .cmsis   = .{ .version = "5.9.0", .hash = "blake3:cbvh...", .kind = .foreign,
                      .urls = .{ "https://github.com/ARM-software/CMSIS_5/archive/5.9.0.tar.gz" } },
        .util    = .{ .path = "../util" },
    },
};

build := (b: &mut std.build.Build) {
    chip := b.dep(.stm32f4, .{ .variant = .f407 });       // parameters, not features
    fw := b.program(.{
        .root = "blinky/app.vun",
        .target = targets.bare.cortex_m4f,
        .deps = .{ .stm32f4 = chip },
        .memory = .{
            .flash = .{ .origin = 0x0800_0000, .len = 512 * 1024 },
            .ram   = .{ .origin = 0x2000_0000, .len = 128 * 1024 },
        },
    });
    b.flash(fw, .probe(.{ .chip = "STM32F407VGTx" }));
    b.test_on(fw, .qemu("lm3s6965"));
    b.lints(.{ .{ std.lints.pedantic, .warn } });
};
```

- `.prelude` lists the namespaces whose public names every file of the package sees
  unqualified, so that tools resolve names from the manifest alone.
- A directory holds a package when its `build.vun` declares `package`. A file belongs to the package
  of the nearest such directory above it. Any other `build.vun` is an ordinary source file, such as
  the namespace `std.build`.
- The package manager identifies a package by the content hash of its `include` tree (section 3),
  and the compiler keys what it caches the same way: packages by that hash, files by the hash of
  their text.
- `package` must be a **literal**: strings, integers, enum literals, and nested anonymous structs
  and tuples. Tools and indexes read it with the ordinary parser, without evaluating anything.
- `build` is ordinary compile-time code with a `&mut Build` capability. It runs in the sandboxed
  evaluator: no I/O, no processes (spec 03, section 7).
- The driver runs `build` through `std.build.plan`, which lends it a `Build` without steps and
  returns the `std.build.Action`s recorded, one per step: `dep`, `program`, `flash`, `test_on`,
  `lints`. The compiler knows neither the name `build`, which it takes from the requirements of
  `std.build.Package`, nor the shape of an action. Records whose types each call infers are kept
  as `lang.meta.Any`. Checking a package's `build.vun` runs its plan, so a trap in `build` is an
  error there; `vun debug plan build.vun` prints the actions, one literal per line.
- `std.build.Build` records a plan of steps, which the driver carries out once `build` returns:
  `b.dep($name, params) -> Dep` names a dependency of `package.deps` (a `lang.meta.Name`, so
  `.stm32f4`) with the parameters its own `build.vun` declares; `b.program(options) -> Program`
  takes a record with `root`, `target`, `deps` and `memory`; `b.flash(program, method)` with a
  `std.build.Flash` (`.probe(.{ .chip = ... })`, `.uf2`, `.dfu`); `b.test_on(program, runner)`
  with a `std.build.Runner`; `b.lints(levels)` with pairs of a lint and a level. What only the
  package knows, names and parameters, is written as records (spec 02, section 2), whose types
  are inferred and which the driver reads by reflection.
- Everything configurable in a project is configured here, in Vun: dependencies, targets, memory
  maps, lints, profiles, flash methods, test targets. There is no second configuration format.

## 3. Dependencies

- **Identity.** A package is identified by `(id, major version)`. A version is identified by the
  content hash of its `include` tree, written `blake3:` followed by the digest in lowercase base32
  without padding (52 characters, safe in file names on file systems that ignore case). The
  algorithm is named so that another can follow; a hash of an unknown algorithm is an error.
- **Tree hash.** The hash is a Merkle tree over directory entries. A file's node is the BLAKE3 hash
  of its contents; a directory's is the BLAKE3 hash, in a key derived from a context string reserved
  for directories, of its entries in name order: a kind (file, executable file or directory), the
  name as one path component, and the child's hash. Being executable is the one mode a package
  keeps, since vendor trees ship scripts such as `configure`; elsewhere than Unix no file is. Paths are components, never separators, so a tree hashes the
  same on every platform; a mismatch can name the file that differs; and a file's hash is the one
  the compiler's caches already use, so nothing is hashed twice. BLAKE3 is also the only hash the
  toolchain uses, for caches as well: measured at 2 to 3 GiB/s on one core and 12 GiB/s on 14,
  against 1.4 GiB/s for SHA-256 with hardware support.
- **Store.** Fetched packages are kept in one store per user, shared by every project:
  `vun/store` in the user's cache directory (`~/.cache` on Unix, including macOS, as command-line
  tools expect; the known folder on Windows), or the directory `VUN_STORE` names. Entries nest by
  the hash alone, `<store>/blake3/<first 2 digest characters>/<remaining 50>/`, so the first level
  has at most 1024 directories. An entry holds the unpacked `package/`, the `snapshot` it was
  verified with (one `hash mode path` line per file, the mode `-` or `x` for executable), and a
  `label` with the name and version it was declared under, for people; the hash stays the only key.
  Loading a stored package recomputes its tree hash; a difference is `package.hash_mismatch`, which
  names every file added, removed or modified since the fetch.
- **Roots and collection.** Writing a lockfile registers its project under `<store>/roots/`. `vun
  cache gc` keeps every entry a registered lockfile records, removes the rest and all staging, and
  forgets projects whose lockfile is gone; `vun cache list` shows each entry's size, label and
  whether a lockfile keeps it.
- **Fetching.** `vun pkg fetch` walks the dependency graph from the project and stores every
  archive dependency the store lacks. Mirrors are tried in order; an archive is unpacked under
  `<store>/staging/`, verified against the declared hash, and moved into its entry only then,
  so the store never holds unverified contents. When every mirror fails, `package.fetch_failed`
  lists each mirror with the chain of causes (spec 10).
- **Adding.** `vun pkg add <source>` declares a dependency in `build.vun`. A directory is declared
  by its path from the project. An archive URL is fetched once and trusted on first use: its tree
  hash is computed, the package is stored, and the entry records that hash and the URL as its first
  mirror, so every later fetch is checked against it. The name and version come from the package's
  manifest; an archive without one is foreign and takes them from `--name` and `--version`. The
  entry is written as a literal (the reader's inverse), into `.deps` or a new `.deps`, keeping the
  manifest's layout.
- **Archives.** There is no bespoke archive format: packages are published as `.tar.zst` (a
  ustar archive in one zstd frame, written by the pure-Rust encoder at its fastest level, about
  zstd's level 1), the files under one `<name>-<version>/` directory, in snapshot order, with no
  timestamps, owners or modes other than the executable bit, so identical trees give identical
  archives. What is unpacked is checked against the tree hash before it is stored. Snapshot paths
  are plain components (no `..`, no separators, no characters special on some platform), so an
  archive cannot write outside its tree. Archives are read as `.tar.zst`, `.tar.xz`, `.tar.gz`,
  `.tar` and `.zip`; their single top-level directory, as forges produce, is dropped. A tar archive may name paths through
  ustar, GNU long-name or PAX `path` records; it holds files and directories only, since a
  package tree has no links, and a link is refused. Schemes (`https`, `http`, `file`) and
  formats are tables, so another is one entry, and every format both reads and writes. `vun pkg
  pack` writes the project's `<name>-<version>.tar.zst` and prints its hash; `--out` ending in
  another format's suffix writes that format instead, with the same fixed metadata, so every
  format is reproducible and unpacks to the same tree hash.
- **Updating.** `vun pkg update` raises each stored dependency to the newest release of its major
  that the root manifest's indexes list (`.index = .{ "https://index.example" }`, tried in order).
  An index speaks a protocol in the style of Go's module proxy: `<index>/<id>/<major>/list` holds
  one `version hash` line per release and `<index>/<id>/<major>/<version>.tar.zst` the archive, the
  identity written as in the lockfile. The release is verified against the listed hash before it
  is stored, its `.deps` entry is rewritten through the literal writer, and the lockfile follows.
- **Sources.** URLs are a mirror list. Any mirror, the local store, or a vendor directory serving the
  right bytes is equally valid. An optional community index (a cache and a transparency log in the
  style of Go's proxy and checksum database) may exist; it is never an authority.
- **Resolution: minimal version selection per `(id, major)`.** Declared versions are minimums; the
  selected version is the largest minimum anywhere in the graph. Different majors are different
  packages and coexist. There are no version ranges and no solver, so resolution is a pure function
  of the manifests.
- **Replacement.** The root manifest may replace an identity anywhere in the graph, for a fork or
  a vendor fix: `.replace = .{ .hal = .{ .id = 0xc0ffee01, .major = 2, .path = "../hal" } }`, or
  `.version`, `.hash` and `.urls` for a stored package. Every dependency on that identity resolves
  to the replacement, its own dependencies are walked instead of the replaced ones, and the
  lockfile records it in `replace`. Only the project's replacements apply, so a
  dependency's cannot change another's build.
- **Parameters, not features.** `b.dep(.x, params)` instantiates a dependency with compile-time
  parameters. Each distinct parameter set is a distinct instantiation. Nothing unifies behind a
  dependent's back; two instantiations that each claim `Peripherals` is a visible type error.
- **Foreign packages** (`.kind = .foreign`) are source archives without a `build.vun`: C libraries,
  vendor SDKs. The dependent's build describes how to compile them (section 8).

## 4. The lockfile

`lock.vun`, beside `build.vun`, records every version the graph requires and the hash it was
verified against. It is a Vun literal file, read without evaluation and written by the literal
writer as manifests are (there is no second data format), and it is no source namespace. Each entry
is one line, sorted, with no whole-file hash, so merges never conflict. The selected version of an
identity is the largest recorded; recording the others too keeps in the store what reading the
graph needs, as `go.sum` does:

```vun
/// Written by `vun pkg` from the selected versions; do not edit.
version := 1;
deps := .{
    .{ .name = "cmsis", .version = "5.9.0", .id = .foreign, .hash = "blake3:cbvh..." },
    .{ .name = "hal", .version = "2.1.4", .id = .{ .id = 3237998081, .major = 2 }, .hash = "blake3:k2mq...", .via = "stm32f4" },
    .{ .name = "stm32f4", .version = "1.3.0", .id = .{ .id = 7674294248581040127, .major = 1 }, .hash = "blake3:x7fa..." },
};
```

`version` is the layout of the file. An entry is the name its first dependent binds, the selected
version, the identity (`.foreign`, or the id and the major version), the tree hash, and the
dependent that requires it when that is not the project. `vun pkg fetch` and `vun pkg add`
rewrite it when the selection changes. Every dependency of every package resolves to the version
selected for its identity, so a dependent declaring `1.0.0` sees `1.2.0` when another requires it;
a lockfile that does not record the selection is `package.stale_lock`, reported at each entry it
should not hold, and one version required with two hashes is `package.version_conflict`, reported
at both dependents; a conflict writes no lockfile.

Selection runs over the packages present. While some are absent (not fetched, or changed in the
store), the lockfile is neither judged nor written, and dependencies resolve through it, since it
recorded the whole graph: an absent package is then reported where it is needed, once, and never
silently replaced by another version. Without a lockfile, the present packages decide. `vun pkg
fetch` walks the graph as declared rather than as selected, so it fills the store and rewrites a
stale lockfile without consulting it. Replacements are listed in `replace`, one per line:
`.{ .name, .id, .hash }` for a stored package or `.{ .name, .id, .path }` for a directory. A pinned
toolchain will add a `toolchain` declaration (section 6).

## 5. Workspaces

A root `build.vun` may declare `.members = .{ "pkgs/hal", "pkgs/app" }`. Members share one lockfile
and one `.vun/`, and refer to each other by path. `vun pkg tag` releases members, running the API
diff (section 7) first.

## 6. Toolchain

`vun` is a small launcher. It reads `.toolchain` from the nearest `build.vun`, fetches that exact
toolchain (hash-checked and recorded in the lock) into `~/.cache/vun/toolchains`, and runs it.
`vun toolchain list|install|prune` manages the cache.

## 7. The command line

One binary, subcommands grouped by what they act on. The CLI is a thin shell over `vun-driver`
(spec 13).

| Command | Does |
|---------|------|
| `vun new <name> [--lib] [--board <b>]` | create a package |
| `vun build`, `vun run` | build, build and run |
| `vun check [--traps] [--widen] [--meta-stats]` | analyze without code generation |
| `vun test [--on interp\|native\|qemu\|probe]`, `vun bench`, `vun fuzz <test>`, `vun sim` | spec 11 |
| `vun fmt [--check]` | format; no options |
| `vun fix [--unsafe] [--edition]` | apply fixes (spec 10) |
| `vun doc` | HTML and JSON API docs; doc code blocks run as tests |
| `vun explain <diagnostic>` | offline explanation pages |
| `vun pkg add\|update\|fetch\|pack\|vendor\|why\|tag` | dependencies and releases |
| `vun pkg api [diff <old>]` | public API and the version bump it requires |
| `vun tool bind <header>`, `vun tool header`, `vun tool svd <file>` | C bindings, C headers, register packages |
| `vun target flash\|attach\|debug` | flash, stream logs, GDB server (section 9) |
| `vun toolchain list\|install\|prune\|components` | toolchains, and this one's backends and linkers |
| `vun cache list\|gc` | the shared store: entries, sizes, labels; collection by lockfile roots |
| `vun util lsp\|completion` | infrequently used: the language server, shell completions |
| `vun debug tokens\|cst\|hir\|mir\|layout\|program\|lir\|code\|frames\|link <file>` | every representation with origins (spec 10) |
| `vun debug compare <file>` | build and run through every backend that generates code; report whether they agree |

Commands are organized as jj's are: everyday verbs at the root, each noun a group of verbs,
infrequent commands under `util`, and commands for developing the compiler under `debug`.

### Conventions enforced by tools

- **fmt** has no configuration; output is stable within an edition.
- **Lints** and naming and organization rules are spec 10, configured in `build.vun`.
- **Editions** are per package; `vun fix --edition` migrates.
- **API diff.** `vun pkg api diff` compares the public API (reflection over non-underscored
  declarations) and refuses a release whose version bump is smaller than the change requires. It
  checks types and signatures, not behavior, and says so.
- **Docs.** A namespace's summary is the first line of its `//!` comment. `vun doc` emits static
  HTML plus JSON for the LSP and indexes.

## 8. C and vendor SDK interop

Wrap the vendor's tree; never repackage it.

**C inside Vun.**
- `b.c_library(.{ .sources, .include, .defines })` compiles C through the configured C toolchain.
- `b.cmake(.{ .source = dep, .outputs = .{ "libfoo.a" } })` runs a vendor CMake build as a declared
  step with declared outputs.
- `vun tool bind` runs against the step's `compile_commands.json` and generated configuration
  headers, so bindings match the real build's macros.

**Vun inside a vendor build.**
- `vun build --emit staticlib --header` produces a library and a C header.
- The toolchain ships `vun.cmake` with `vun_add_library(name DIR ...)`.
- A package can ship an `idf_component.yml` (ESP-IDF) and a `zephyr/module.yml` (Zephyr, pulled in
  by west) that call it. The SDK keeps ownership of startup, linking and its component manager.

**Build steps.** Tool steps (C compilers, CMake, `vun tool bind`) are nodes in the build graph
with declared inputs and outputs. The driver runs them and caches each by the hash of (tool, its
arguments, its inputs). On Linux they run inside a namespace sandbox that exposes only the declared
inputs. The cache keys are designed to work with a remote cache later.

## 9. Embedded tooling

- **Flash and debug.** probe-rs and espflash are linked into the driver as Rust libraries, so
  `vun target flash`, `attach` (log stream) and `debug` (GDB server) support CMSIS-DAP, ST-Link,
  J-Link and ESP USB-JTAG without external runners. `b.flash(fw, .probe(...) | .serial(...) | .uf2
  | .command(...))` declares how a program is flashed.
- **Deferred logging is library code.** `std.log.info("t={} v={}", .{ t, v })` parses its format
  string at compile time, emits the string into a `#[link.section(".vun.log.info")]` constant in
  a non-loaded section, and at run time writes only the string's index and the packed arguments to
  a transport (RTT, UART, USB). `vun target attach` decodes using the ELF. Level filtering happens
  at compile time. Trap messages use the same table (spec 07).
- **Register packages** are generated with `vun tool svd` into checked-in Vun source (plain
  register values in the style of chiptool, not ownership singletons), so diffs and docs are
  visible. For small parts, `svd.Peripheral` can do the same at compile time from `std.meta.embed`
  (spec 03); the generator is the same code.
