# 12. Ecosystem: packages, project layout, tooling

Research notes, section 2, has the survey. The short version of what is copied and why:

| Copied | From | Because |
|--------|------|---------|
| content hash as package identity, URLs as mirrors | Zig, Nix, Roc | integrity without a central authority |
| minimal version selection, new major = new package | Go | deterministic, no solver, explainable |
| sorted line-per-entry integrity file | Go (`go.sum`) | conflict-free merges |
| toolchain pin with automatic download | Go, rustup | reproducible builds from a checkout |
| one formatter, whose one option is the width of a line | gofmt, zig fmt | few style debates |
| API-computed version bumps | Elm, cargo-semver-checks | semver that means something |
| deferred logging | defmt | logs cost an index and packed bytes on the device |
| flashing and debugging as libraries | probe-rs, espflash | one CLI, no external runner |

| Avoided | Seen in | Because |
|---------|---------|---------|
| graph-wide additive features | Cargo | one dependent silently changes another's build |
| arbitrary code at build or fetch time | `build.rs`, dependencies' `build.zig` | unsandboxed, uncacheable |
| file-name conventions selecting code | Go `_linux.go`, Hare `+linux` | invisible selection |
| a single URL per dependency | Zig | a dead host breaks the build |
| a mandatory central registry | most ecosystems | governance burden, single point of failure |
| repackaging vendor SDKs | PlatformIO | lags vendors, forks the ecosystem |
| a bespoke data format | ZON | every tool needs a new parser |

## 1. Project layout

```
blinky/
  build.vun              manifest and build graph (section 2)
  lock.vun               generated, committed (section 4)
  blinky.vun             the package namespace: doc comment, re-exports, top-level declarations
  blinky/               its children (spec 01, section 8)
    app.vun              root file of the firmware program
    serial.vun
    serial/
      uart.vun
      _registers.vun     private to serial/
  tests/                integration tests: a test package that depends on this one
  tests/reject/         must-fail files with expected diagnostics
  tests/snapshots/      snapshot files
  examples/             one program per file, `vun build --example name`
  benches/              benchmark tests
  fuzz/                 corpus and crash inputs, per test
  docs/                 guides; API docs come from doc comments
  vendor/               only after `vun pkg vendor`
  .vun/               the project's builds, saved queries and editor views, ignored by version control and never package content; one per project, a workspace's at its root
```

No directory name is significant to the compiler except through `build.vun`, which states the roots.
The layout above is what `vun new` creates and what the `layout` lints expect.

## 2. The manifest is `build.vun`

`build.vun` is a Vun file conforming to the interface `std.build.Package`, which requires two
declarations: `package` and `build`. They are required by that interface, not by the compiler.

```vun
//! Blinky: an LED and a serial echo on an STM32F4.

package := .{
    .name = "blinky",
    .id = 0x6a80_91f5_7c7f_07ff,          // generated by `vun new`; survives renames
    .version = "0.3.1",
    .edition = 2026,
    .toolchain = "0.4.2",                 // exact; another `vun` hands off to it (section 6)
    .target = "bare.thumbv7em.eabihf",    // what the package is written for; the machine's when absent
    .include = .{ "build.vun", "blinky.vun", "blinky", "LICENSE" },   // what the hash covers
    .prelude = .{ "std.prelude" },        // the default; `.{}` for none (spec 01, section 8)
    .deps = .{
        .stm32f4 = .{ .version = "1.3.0", .hash = "blake3:x7fa...",
                      .urls = .{ "https://git.example.org/stm32f4/1.3.0.tar.gz" } },
        .cmsis   = .{ .version = "5.9.0", .hash = "blake3:cbvh...", .kind = .foreign,
                      .urls = .{ "https://github.com/ARM-software/CMSIS_5/archive/5.9.0.tar.gz" } },
        .util    = .{ .path = "../util" },
    },
};

build := (b: &mut std.build.Build) {
    chip := b.dep(.stm32f4, .{ .variant = .f407 });       // parameters, not features
    fw := b.program(.{
        .root = "blinky/app.vun",
        .target = targets.bare.thumbv7em.eabihf,
        .deps = &[.{ .name = .stm32f4, .dep = chip }],
        .memory = &[
            .{ .name = .flash, .origin = 0x0800_0000, .len = 512 * 1024 },
            .{ .name = .ram,   .origin = 0x2000_0000, .len = 128 * 1024 },
        ],
    });
    b.flash(fw, .probe(.{ .chip = "STM32F407VGTx" }));
    b.test_on(fw, .qemu("lm3s6965"));
    b.lints(.{ .{ std.lints.pedantic, .warn } });
};
```

- `.prelude` lists the namespaces whose public names every file of the package sees
  unqualified, so that tools resolve names from the manifest alone.
- A directory holds a package when its `build.vun` declares `package`. A file belongs to the package
  of the nearest such directory above it. Any other `build.vun` is an ordinary source file, such as
  the namespace `std.build`.
- The package manager identifies a package by the content hash of its `include` tree (section 3),
  and the compiler keys what it caches the same way: packages by that hash, files by the hash of
  their text.
- `package` must be a **literal**: strings, integers, enum literals, and nested anonymous structs
  and tuples. Tools and indexes read it with the ordinary parser, without evaluating anything.
- `build` is ordinary compile-time code with a `&mut Build` capability. It runs in the sandboxed
  evaluator: no I/O, no processes (spec 03, section 7).
- The driver runs `build` through `std.build.plan`, which lends it a `Build` without steps and
  returns the `std.build.Action`s recorded, one per step: `dep`, `program`, `flash`, `test_on`,
  `lints`. The compiler does not know the name `build`, which it takes from the requirements of
  `std.build.Package`, and reads each action member by member through the generated handles of
  `std.build`'s declarations, never a name written as text. Records whose types each call infers are kept
  as `lang.meta.Any`. Checking a package's `build.vun` runs its plan, so a trap in `build` is an
  error there; `vun debug dump plan build.vun` prints the actions, one literal per line.
- `std.build.Build` records a plan of steps, which the driver carries out once `build` returns:
  `b.dep($name, params) -> Dep` names a dependency of `package.deps` (a `lang.meta.Name`, so
  `.stm32f4`) with the parameters its own `build.vun` declares; `b.program(options) -> Program`
  takes a `std.build.Options`: its `root` file, its `target` (a `lang.target.Spec`), the `deps`
  it uses (`std.build.Use`: a name and the `Dep` a step built), its `memory` map
  (`std.build.Region`: a name, an origin and a length) and the `sections` placed in it
  (`std.build.Placement`: a section, the region holding it and the region it loads from, if
  another), the last three empty unless given;
  `b.flash(program, method)` with a
  `std.build.Flash` (`.probe(.{ .chip = ... })`, `.uf2(.{ .family = ... })`, `.dfu`); `b.test_on(program, runner)`
  with a `std.build.Runner`; `b.lints(levels)` with pairs of a lint and a level. What only the
  package knows, names and parameters, is written as records (spec 02, section 2), whose types
  are inferred and which the driver reads by reflection.
- `vun build` on a package (its directory, its `build.vun`, or no path inside it) carries out the plan in order: each program is built in a session for its
  own target, its root relative to the `build.vun`, its memory map placed by the link plan. Steps
  the toolchain does not carry out yet (`flash` through a probe or DFU, `test_on`, dependency
  parameters, lint levels) are warnings (`plan.unsupported`); a `uf2` flash step writes the
  program's loadable segments as a `.uf2` file beside it, for a device whose boot ROM takes
  blocks over USB mass storage (`plan.unflashed` when it cannot); a step that is not a `std.build.Action` as `std.build`
  declares it is `plan.unread`.
- Everything configurable in a project is configured here, in Vun: dependencies, targets, memory
  maps, lints, profiles, flash methods, test targets. There is no second configuration format.
- **Commands.** `b.commands(.{ .fmt = .{ .width = 100 }, .fuzz = .{ .cases = 5000 } })` gives the
  options of commands the values to use where neither the command line nor the environment gives
  one: a section for each command, a field for each of its options, named as `--help` names them
  (a number, a name, a string, a tuple of them for an option taking several, `true` for a flag).
  Any option of a command naming a path (`fmt`, `check`, `build`, `run`, `test`, `fuzz`, ...) can
  be set, so no default is fixed in the toolchain; the package around the path the command is
  given, or this directory, is the one read. A section or a field that is no command or option
  is `plan.unknown_setting`, a value an option does not take its usual usage error.

## 3. Dependencies

- **Identity.** A package is identified by `(id, major version)`. A version is identified by the
  content hash of its `include` tree, written `blake3:` followed by the digest in lowercase base32
  without padding (52 characters, safe in file names on file systems that ignore case). The
  algorithm is named so that another can follow; a hash of an unknown algorithm is an error.
- **Tree hash.** The hash is a Merkle tree over directory entries. A file's node is the BLAKE3 hash
  of its contents; a directory's is the BLAKE3 hash, in a key derived from a context string reserved
  for directories, of its entries in name order: a kind (file, executable file or directory), the
  name as one path component, and the child's hash. Being executable is the one mode a package
  keeps, since vendor trees ship scripts such as `configure`; elsewhere than Unix no file is. Paths are components, never separators, so a tree hashes the
  same on every platform; a mismatch can name the file that differs; and a file's hash is the one
  the compiler's caches already use, so nothing is hashed twice. BLAKE3 is also the only content
  hash the toolchain uses, for caches as well (in-memory identities and query fingerprints use a
  fixed-seed fast hash, stable within one toolchain build, spec 13): measured at 2 to 3 GiB/s on one core and 12 GiB/s on 14,
  against 1.4 GiB/s for SHA-256 with hardware support.
- **What a package is.** A manifest's `include` names `build.vun`: a package's hash covers its
  manifest. Include entries are paths inside the package, with no root and no `..`
  (`manifest.invalid_field`). A stored package names its dependencies and replacements by hash;
  a path is refused. An archive holds at most 65536 entries and 512 MiB of files, and is read up
  to 1 GiB; links and other non-regular entries are refused. Network sources are `https://`
  only: another scheme is refused when the source is read, before any request, and a local
  mirror is a `file://` source. A download takes at most 10 minutes and follows at most 8
  redirects itself, one hop at a time, each target read against the URL it leaves and requested
  only if it is `https://` (decision 248). `vun pkg update` takes the newest
  release of the dependency's major and checks that it declares the identity and version it is
  listed under.
- **Store.** A fetch stages in a directory of its own process under `staging/`, holding the
  store's lock shared; collection takes it alone. An entry another process stored first is kept,
  as it holds the same contents. Fetched packages are kept in one store per user, shared by every project:
  `vun/store` in the user's cache directory (`~/.cache` on Unix, including macOS, as command-line
  tools expect; the known folder on Windows), or the directory `VUN_STORE` names. Entries nest by
  the hash alone, `<store>/blake3/<first 2 digest characters>/<remaining 50>/`, so the first level
  has at most 1024 directories. An entry holds the unpacked `package/`, the `snapshot` it was
  verified with (one `hash mode path` line per file, the mode `-` or `x` for executable), and a
  `label` with the name and version it was declared under, for people; the hash stays the only key.
  Loading a stored package recomputes its tree hash; a difference is `package.hash_mismatch`, which
  names every file added, removed or modified since the fetch.
- **Roots and collection.** Writing a lockfile registers its project under `<store>/roots/`. `vun
  cache gc` keeps every entry a registered lockfile records, removes the rest and all staging, and
  forgets projects whose lockfile is gone; `vun cache list` shows each entry's size, label and
  whether a lockfile keeps it.
- **Fetching** is implicit: before compiling (`vun build`, `vun run`, `vun check`) and after
  `vun pkg update`, the dependency graph is walked from the project and every archive dependency
  the store lacks is stored, each download shown as a `Downloaded` status line. Mirrors are tried in order; an archive is unpacked under
  `<store>/staging/`, verified against the declared hash, and moved into its entry only then,
  so the store never holds unverified contents. When every mirror fails, `package.fetch_failed`
  lists each mirror with the chain of causes (spec 10).
- **Adding.** `vun pkg add <source>` declares a dependency in `build.vun`. A directory is declared
  by its path from the project. An archive URL is fetched once and trusted on first use: its tree
  hash is computed, the package is stored, and the entry records that hash and the URL as its first
  mirror, so every later fetch is checked against it. The name and version come from the package's
  manifest; an archive without one is foreign and takes them from `--name` and `--version`. The
  entry is written as a literal (the reader's inverse), into `.deps` or a new `.deps`, keeping the
  manifest's layout.
- **Archives.** There is no bespoke archive format: packages are published as `.tar.zst` (a
  ustar archive in one zstd frame, written by the pure-Rust encoder at its fastest level, about
  zstd's level 1), the files under one `<name>-<version>/` directory, in snapshot order, with no
  timestamps, owners or modes other than the executable bit, so identical trees give identical
  archives. What is unpacked is checked against the tree hash before it is stored. Snapshot paths
  are plain components (no `..`, no separators, no characters special on some platform), so an
  archive cannot write outside its tree. Archives are read as `.tar.zst`, `.tar.xz`, `.tar.gz`,
  `.tar` and `.zip`; their single top-level directory, as forges produce, is dropped. A tar archive may name paths through
  ustar, GNU long-name or PAX `path` records; it holds files and directories only, since a
  package tree has no links, and a link is refused. Mirrors and indexes are URLs (RFC 3986),
  checked when the manifest is read; a local mirror is a file URL (RFC 8089), its path escaped
  (`file:///srv/a%20b.tar.zst`). Schemes (`https`, `file`) and
  formats are tables, so another is one entry, and every format both reads and writes. `vun pkg
  pack` writes the project's `<name>-<version>.tar.zst` and prints its hash; `--out` ending in
  another format's suffix writes that format instead, with the same fixed metadata, so every
  format is reproducible and unpacks to the same tree hash.
- **Updating.** `vun pkg update` raises each stored dependency to the newest release of its major
  that the root manifest's indexes list (`.index = .{ "https://index.example" }`, tried in order).
  An index speaks a protocol in the style of Go's module proxy: `<index>/<id>/<major>/list` holds
  one `version hash` line per release and `<index>/<id>/<major>/<version>.tar.zst` the archive, the
  identity written as in the lockfile. The release is verified against the listed hash before it
  is stored, its `.deps` entry is rewritten through the literal writer, and the lockfile follows.
- **Sources.** URLs are a mirror list. Any mirror, the local store, or a vendor directory serving the
  right bytes is equally valid. An optional community index (a cache and a transparency log in the
  style of Go's proxy and checksum database) may exist; it is never an authority.
- **Resolution: minimal version selection per `(id, major)`.** Declared versions are minimums; the
  selected version is the largest minimum anywhere in the graph. Different majors are different
  packages and coexist. There are no version ranges and no solver, so resolution is a pure function
  of the manifests.
- **Replacement.** The root manifest may replace an identity anywhere in the graph, for a fork or
  a vendor fix: `.replace = .{ .hal = .{ .id = 0xc0ffee01, .major = 2, .path = "../hal" } }`, or
  `.version`, `.hash` and `.urls` for a stored package. Every dependency on that identity resolves
  to the replacement, its own dependencies are walked instead of the replaced ones, and the
  lockfile records it in `replace`. Only the project's replacements apply, so a
  dependency's cannot change another's build.
- **Parameters, not features.** `b.dep(.x, params)` instantiates a dependency with compile-time
  parameters. Each distinct parameter set is a distinct instantiation. Nothing unifies behind a
  dependent's back; two instantiations that each claim `Peripherals` is a visible type error.
- **Foreign packages** (`.kind = .foreign`) are source archives without a `build.vun`: C libraries,
  vendor SDKs. The dependent's build describes how to compile them (section 8).

## 4. The lockfile

`lock.vun`, beside `build.vun`, records every version the graph requires and the hash it was
verified against. It is a Vun literal file, read without evaluation and written by the literal
writer as manifests are (there is no second data format), and it is no source namespace. Each entry
is one line, sorted, with no whole-file hash, so merges never conflict. The selected version of an
identity is the largest recorded; recording the others too keeps in the store what reading the
graph needs, as `go.sum` does:

```vun
/// Written by `vun pkg` from the selected versions; do not edit.
version := 1;
deps := .{
    .{ .name = "cmsis", .version = "5.9.0", .id = .foreign, .hash = "blake3:cbvh..." },
    .{ .name = "hal", .version = "2.1.4", .id = .{ .id = 3237998081, .major = 2 }, .hash = "blake3:k2mq...", .via = "stm32f4" },
    .{ .name = "stm32f4", .version = "1.3.0", .id = .{ .id = 7674294248581040127, .major = 1 }, .hash = "blake3:x7fa..." },
};
```

`version` is the layout of the file. An entry is the name its first dependent binds, the selected
version, the identity (`.foreign`, or the id and the major version), the tree hash, and the
dependent that requires it when that is not the project. Compiling, `vun pkg add` and `vun pkg
update` rewrite it when the selection changes. Every dependency of every package resolves to the version
selected for its identity, so a dependent declaring `1.0.0` sees `1.2.0` when another requires it;
a lockfile that does not record the selection is `package.stale_lock`, reported at each entry it
should not hold, and one version required with two hashes is `package.version_conflict`, reported
at both dependents; a conflict writes no lockfile.

Selection runs over the packages present. While some are absent (not fetched, or changed in the
store), the lockfile is neither judged nor written, and dependencies resolve through it, since it
recorded the whole graph: an absent package is then reported where it is needed, once, and never
silently replaced by another version. Without a lockfile, the present packages decide. Fetching,
implicit before every compiling command (decision 181), walks the graph as declared rather than as
selected, so it fills the store and rewrites a stale lockfile without consulting it. Replacements are listed in `replace`, one per line:
`.{ .name, .id, .hash }` for a stored package or `.{ .name, .id, .path }` for a directory. A pinned
toolchain is recorded as `toolchain := .{ .version, .hash }` (section 6).

## 5. Workspaces

A root `build.vun` may declare `.members = .{ "pkgs/hal", "pkgs/app" }`, directories below it each
holding a package. The root is a package too, and with its members it is one project: its graph
is theirs together, the root's `toolchain` and `replace` apply to them, and they share the root's
lockfile, which records every member's dependencies, and its `.vun/`. Members refer to each other by path. A
member whose directory holds no package is `package.missing_member`. A command given the root's
directory, or no path at or below the root outside any member, acts on each package of the
workspace, the root first (section 7); given a member's, or no path inside one, on that member.
`vun pkg tag`
releases members, running the API diff (section 7) first.

## 6. Toolchain

Four things decide how a program is built, each declared in one place:

| Name | Is | Where |
|------|----|-------|
| toolchain | one release of `vun`: the executable and its library | a directory, `~/.local/share/vun/toolchains/<version>/` once installed |
| target | what a program runs on: a `lang.target.Spec` | the package `targets`, `targets.<os>.<arch>.<abi>` (spec 13, section 7) |
| component | a backend or a linker compiled into the toolchain | the toolchain's executable |
| tools | the programs of this machine building and running for a target | the machine's tools file |

`vun toolchain show` says which toolchain runs and what it holds; `vun target list` lists the
targets with what builds for each and what the machine lacks; `vun target show` gives every part
of a build for the chosen target, where each program is and why each part is the one (the
target's declaration, an option, a line of the tools file).

**The toolchain's directory.** A toolchain is a directory holding the executable `bin/vun` and
its library in `lib/`: the packages `lang`, `std`, `targets` and `boards`, and the pages of
`vun explain`. A release archive unpacks to one. `vun` reads the library the environment
variable `VUN_LIBRARY` names, else `lib/` beside its own `bin/` when that holds every default
dependency, else the checkout it was built from, which is how development builds run.

**A toolchain under WASI.** `vun` also builds for `wasm32-wasip1`, where a program has no home,
starts no process and no thread, and loads no library. There it is a user without a home: the
store is kept in the working directory and the tools file is only the one `VUN_TOOLS` names;
`vun ffi`, which loads libclang, is left out; the work spread over threads elsewhere runs on the
one thread; the executable is the file its first argument names, which the host starting it
sets, and the library the one beside it or `VUN_LIBRARY` names. The playground runs it in a
browser, a toolchain's tree in a file system held in memory, building for `wasi.wasm32.p1`,
whose linker runs in process (spec 13, section 8.4); the memos it saves are kept between runs
and visits.

**Installing and pinning.** Toolchains are installed side by side, one directory per version,
from the releases of the project's repository, each tagged with its version as it is (`0.4.2`),
or from the base `VUN_RELEASES` names (a mirror, or a directory as a `file:` URI), laid out as a
forge lays releases out. Each release carries a manifest, `release.json`, naming for each machine
(`arch` and `os`, as targets name them) its archive, `vun-<arch>-<os>.tar.gz`, and the BLAKE3
hash of the toolchain tree the archive unpacks to, `bin/`, `lib/` and `LICENSES/`, which is
checked before anything is kept. The manifest is signed: `release.json.sig` is the Ed25519
signature of its bytes, checked against the key `vun` is built with, or the one
`VUN_RELEASES_KEY` names (`ed25519:<base32>`, for a mirror signing its own), so the manifest and,
through its hashes, every archive are the project's. An installed toolchain keeps its manifest. `vun toolchain list|install|remove|update` manages them;
`update` installs the latest release and makes it the default, the one `~/.local/bin/vun` links
to; the default and the running toolchain are not removed. A first installation runs the
repository's `install.sh`, which unpacks this machine's archive of the latest release somewhere
temporary and lets it run `vun toolchain update`.

A package pins a toolchain with `.toolchain` in its `build.vun`. A `vun` loading a project that
pins another version installs that version when missing and hands the command to it (it replaces
the process), so no launcher stands apart from the toolchains; the toolchain handed to runs as
itself (`VUN_TOOLCHAIN=local`, which also keeps the running one anywhere). The lockfile records
the pinned release as `toolchain := .{ .version, .hash }`, the hash of its manifest's bytes, which
names every machine's toolchain at once; a `vun` handing off refuses a manifest of that version
hashing otherwise, and installs again a toolchain installed from another. A first installation
trusts the toolchain `install.sh` fetches as far as the connection; the `vun toolchain update` it
runs checks the signature.

**The machine's tools file.** A target names its own tools (`lang.target.CCompiler`), which
fit a machine of that target: a C compiler building for the target (`builds_for = .target`, a
cross compiler or one told the target), or the system's own `cc`, which builds for the machine
it runs on (`builds_for = .host`). Building for another machine needs other tools, a cross C
compiler and an emulator to run what it built, and where they are is a fact of the machine, not
of the target. The file `vun/tools.vun` in the user's configuration directory (or the one
`VUN_TOOLS` names) says it, read as literal data like a manifest:

```vun
tools := .{
    .targets = .{
        .{
            .target = linux.arm64.kernel,
            .compiler = "aarch64-linux-gnu-gcc",
            .sysroot = "/usr/aarch64-linux-gnu",
            .runner = .{ "qemu-aarch64", "-L", "/usr/aarch64-linux-gnu" },
        },
        .{ .target = macos.arm64.darwin, .sysroot = "/opt/sdk/MacOSX.sdk" },
        .{
            .target = windows.x86_64.msvc,
            .sysroot = "/opt/winlibs",           // the directory holding `kernel32.lib`
            .runner = .{ "wine64" },
        },
        .{
            .target = windows.x86.msvc,
            .sysroot = "/opt/winlibs32",         // `kernel32.lib` and `ntdll.lib` of 32-bit x86
            .runner = .{ "env", "WINEPREFIX=/opt/wine32", "wine" },
        },
    },
};
```

Each entry names a target by its path in the package `targets`, as `--target` does. When the
chosen target is the one an entry names, `.compiler` replaces its C compiler, `.flags` are added
to every run of it (compiling and linking), `.sysroot` is the directory of the target system's
headers and libraries its tools build against (`lang.target.CCompiler.sysroot`: the C compiler's
`--sysroot`, `ld64.lld`'s `-syslibroot`, an SDK for macOS, `lld-link`'s `/libpath:` for Windows), and `vun run`, `vun debug compare` and the backend
tests run programs through `.runner`, the program and its arguments after it. An entry naming no
target is an error (`target.unchosen`); a machine without the file builds with the targets' tools.

## 7. The command line

One binary, `vun`, a thin shell over `vun-driver` (spec 13). Commands are organized as jj's are:
everyday verbs at the root, each noun a group of verbs, infrequent commands under `util`, and
commands for developing the compiler under `debug`. A command exists in the tree once it is
implemented; nothing is listed that does not run.

Every command that compiles takes a path, optional (decision 356): a file, a directory or a
package's directory, and with none the package around the current directory, its nearest
`build.vun`, as cargo finds `Cargo.toml`; the root of a workspace names each of its packages
(section 5). A file outside any package is a program of its own; a directory outside any is
`package.no_project`.

| Command | Does |
|---------|------|

Still to come, each as a verb or a group verb: `new`, `test`, `bench`, `fuzz`, `fix`,
`pkg vendor|why|tag|api`, `ffi header|svd`, `target flash|attach|debug`.

Options:

- **Global**, on every command: `--color <auto|always|never>` (or `VUN_COLOR`), `--format
  <human|json|styled>` (or `VUN_FORMAT`; below), `-q`/`--quiet`
  (results and diagnostics only, no status lines), `-h` (help) and `--help` (the long page,
  through the pager on a terminal: aliases, the values and variables of options, examples),
  and `-V`/`--version` on the root.
- **Compile options**, a set shared by every command that compiles (`build`, `run`, `check`,
  `debug`): `--target <path>` (`VUN_TARGET`), `--diagnostics <format>` (`VUN_DIAGNOSTICS`),
  `--timings`.
- A command's own options, such as `--backend` and `-o`.

Output follows cargo's shell: results go to standard output, progress to standard error as status
lines whose verb is right-aligned in a column (`Checking`, `Building`, `Running`, `Downloaded`,
`Finished` with the time taken, `Failed` with the errors), after the diagnostics of the step.
Colors are decided per stream: `auto` shows them on a terminal unless `NO_COLOR` is set, or
`CLICOLOR_FORCE` forces them, or `CLICOLOR=0` or `TERM=dumb` turns them off.

Output is machine-readable with `--format json`: every line of standard output is then one JSON
object naming its `type`, for results (`component`, `stored`, `dump`, `explanation`, ...), progress
(`started`, `finished` with `success`, `errors`, `warnings` and the time, `downloaded`, ...) and
diagnostics (`diagnostic`, schema in spec 10) alike; logs stay on standard error. Commands report
typed records, each shown both ways, so a command has one output and two views of it.
`--format styled` shows what people read, on the streams they read it on, each line one JSON
object (`"type": "line"`) of its pieces and the style each names (`good`, `strong`, `error`, ...,
the styles of `vun_term::Style`); diagnostics are rendered as for people, without colors. It is
for tools that draw vun's output themselves, as the brand's videos do (`pnpm record`). Global
options are read before the rest of the command line, so a usage error follows them too. A
program that `vun run` starts writes its own output as it pleases.

The framework, `vun-command`, declares a tree as data: commands (name, aliases, parameters, the
option sets they share, examples) and parameters (a flag, an option or a positional; how many
values; what a value may be: text, a path, or a choice among a table's names; the variable
giving a default). Parsing, validation with suggestions, help, and the completion scripts all
read that declaration.

### Conventions enforced by tools

- **fmt** has one option, the width of a line (`--width`, `VUN_FMT_WIDTH`, or `b.commands`); output is
  stable within an edition for the same width.
- **Lints** and naming and organization rules are spec 10, configured in `build.vun`.
- **Editions** are per package; `vun fix --edition` migrates.
- **API diff.** `vun pkg api diff` compares the public API (reflection over non-underscored
  declarations) and refuses a release whose version bump is smaller than the change requires. It
  checks types and signatures, not behavior, and says so.
- **Docs.** A namespace's summary is the first line of its `//!` comment. `vun doc` emits static
  HTML plus JSON for the LSP and indexes. Declarations are read from the CST, each with the kind
  its value's shape shows (function, struct, enum, value); the driver then asks sema which of the
  values are types (the query `vun_sema::decl::Declaration`), so `Word := u32` is documented as a
  type. The documentation model (`vun-doc`) does not depend on sema.

## 8. C and vendor SDK interop

Wrap the vendor's tree; never repackage it.

**C inside Vun.**
- `b.c_library(.{ .sources, .include, .defines })` compiles C through the configured C toolchain.
- `b.cmake(.{ .source = dep, .outputs = .{ "libfoo.a" } })` runs a vendor CMake build as a declared
  step with declared outputs.
- `vun ffi bind` runs against the step's `compile_commands.json` and generated configuration
  headers, so bindings match the real build's macros.

**Vun inside a vendor build.**
- `vun build --library static` produces a library, which the target's archiver
  (`lang.target.CCompiler.archiver`, or the machine's tools file's `archiver`) bundles;
  `vun ffi header` writes its C header.
- The toolchain ships `vun.cmake` with `vun_add_library(name DIR ...)`.
- A package can ship an `idf_component.yml` (ESP-IDF) and a `zephyr/module.yml` (Zephyr, pulled in
  by west) that call it. The SDK keeps ownership of startup, linking and its component manager.

**Build steps.** Tool steps (C compilers, CMake, `vun ffi bind`) are nodes in the build graph
with declared inputs and outputs. The driver runs them and caches each by the hash of (tool, its
arguments, its inputs). On Linux they run inside a namespace sandbox that exposes only the declared
inputs. The cache keys are designed to work with a remote cache later.

## 9. Embedded tooling

- **Flash and debug.** probe-rs and espflash are linked into the driver as Rust libraries, so
  `vun target flash`, `attach` (log stream) and `debug` (GDB server) support CMSIS-DAP, ST-Link,
  J-Link and ESP USB-JTAG without external runners. `b.flash(fw, .probe(...) | .serial(...) | .uf2
  | .command(...))` declares how a program is flashed.
- **Deferred logging is library code.** `std.log.info("t={} v={}", .{ t, v })` parses its format
  string at compile time, emits the string into a `#[link.section(".vun.log.info")]` constant in
  a non-loaded section, and at run time writes only the string's index and the packed arguments to
  a transport (RTT, UART, USB). `vun target attach` decodes using the ELF. Level filtering happens
  at compile time. Trap messages use the same table (spec 07).
- **Register packages** are generated with `vun ffi svd` into checked-in Vun source (plain
  register values in the style of chiptool, not ownership singletons), so diffs and docs are
  visible. For small parts, `svd.Peripheral` can do the same at compile time from `std.meta.embed`
  (spec 03); the generator is the same code.
