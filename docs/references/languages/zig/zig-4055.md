Here's a straightforward example:

```zig
comptime {
    @setEvalBranchQuota(1000000000);
    var x: u32 = 0;
    for (0..100000000) |i| {
        x = i;
    }
}
```

Python equivalent:

```python
x = 0
while x < 100000000:
    x += 1
```

Apologies for the image, but here's a perf measurement:

![image](https://github.com/ziglang/zig/assets/106511/692cf455-e7d5-4b9d-8812-cb1ceee75654)

To summarize, it's 189s in zig comptime vs 6s in CPython, and the zig compiler used 14 GiB of memory.

This is due to the way comptime is currently implemented in zig, and we'll need to make some fundamental changes to the compiler in order to address it. For starters, we need to model comptime-mutable memory as actual mutable memory, rather than tossing everything into the garbage-collected InternPool. This way it's not needed to run garbage collection more than in between compilations, and also do a lot less bookkeeping work for these temporary mutable values.

from https://ziggit.dev/t/implementation-of-comptime/5041/5 my understanding is that the evaluation of comptime happens "inside the compiler" as part of the conversion from ZIR to AIR which is straightforward and probably fast enough for things like Generic Types and Resolving compile time known Constants (fancy C-Macros, which i guess is the primary intended use case!).  

Since we now talking interpreters there probably comes a point where it will be faster to compile and execute more expensive parts as native machine code. maybe this would also prevent us from writing modified compile time versions of functions. 
(comptime fmt(...) instead of comptime_fmt(...))

I wonder if this is in the scope of current development of the zig compiler and how hard it would be to do this (i cant grasp that due to my limited knowledge of compiler internals).
