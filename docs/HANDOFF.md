# Handoff

State of Vun as of 2026-09-29, for the next agent: what is open and what comes next. Nothing here
is durable; conventions and how-tos live in [`dev/`](dev/workflow.md), rules in
[`spec/`](spec/00-principles.md), history in `jj log` and [`decisions.md`](spec/decisions.md).
Read `CLAUDE.md` and [`dev/workflow.md`](dev/workflow.md) first.

## State

Everything is committed in the main chain; no `jj` workspace holds work. 637 tests pass; clippy,
`cargo gen --check`, `lines` and `layers` are clean; the corpus has 295 passing programs.

Built: the front end, packages and the store, the persisted parallel query engine, sema, MIR and
its checks, LIR with legalization, the C and wasm backends, the native backend for x86-64, arm64
and Thumb-2, ELF and Mach-O objects, the `gnu`, `mold` and `wild` linkers, the toolchain file,
static Linux runtimes calling the kernel (threads, storage per thread, files, clocks),
backtraces. Programs run through either backend on linux.x86_64, linux.arm64, linux.arm (through
`qemu`) and wasi.wasm32.

In the working copy, not committed: brand assets. `assets/` nested into `logo/` (SVG wordmark,
mark, icon, construction, sixteen CSS animations in `motion/`) and `cards/` (Typst code, social and
icon cards over the schemes of `assets/palette.toml`), and `assets/motion` (Motion Canvas: the
`sting` video, see `docs/dev/repository.md`); `cargo xtask typeset` expands each card's
`<variants>` metadata and compiles in parallel. Open: removing PNGs of variants no longer
declared, as `cargo gen` does.

Last landed: editor integration, second batch (319 to 321). Productions for every node kind
(`lib/lang/lang/syntax/nodes.vun`, split from `grammar.vun`), checked by the CST verifier
(`NodeKind::spelled_by`) on every tree the parser builds; the tables editors and the parser share
(`parts`, `admits`, `holds`, `precedence`, `unterminated`, `transparent`, `member_names`,
`line_ends`, `preferred`; `open_ended` in `grammar.vun`, which the parser already reads). The
tree-sitter grammar (`editors/tree-sitter`, `vun-tree-sitter`), its queries and the Helix, Neovim,
Zed and VS Code packages, generated by `cargo gen`; `cargo xtask tree-sitter` settles the
conflicts (`conflicts.json`), builds the parser (`src/`, ignored) and compares its trees with the
compiler's: 192 of 198 sources agree. `vun-json` became `vun-data` (JSON, TOML and Lua written from
one model). First batch (316 to 318): `#[derive(ToData, FromData)]`
(`vun-data-derive` on `vun-derive-core`, shared with the codec derive) and `#[derive(Variants)]`;
`vun-uri` (RFC 3986 and 8089, fuzz target `uri`), with manifest `.urls`/`.index`, `vun-fetch`,
`vun-http` redirects and index paths typed through it; `vun-lsp-protocol` (typed LSP values,
methods as types) and the server rebuilt on it, adding incremental sync, the outline, folds,
formatting and semantic tokens (driver side in `vun-driver`'s `editor/`). Before that:
`std.fmt.print` takes its arguments as a pack (315); docs split into `HANDOFF.md`
(state only) and `docs/dev/` (conventions, commands, crates, pitfalls); README rewritten with a
code card (`assets/`), MIT OR Apache-2.0 licensing, `CONTRIBUTING.md`; `design/` removed. Before
that: the `vun-sema` split into the `sema` group (`int`, `float`, `ty`, `core`, `plan`;
primitives in `vun-primitives`), Mach-O arm64 thread-local variables (314), a thread's backtrace
naming the calls that spawned it (313).

## Known gaps in landed work

- A `$`-generic C import (a pack inferred per call) is typed nowhere yet: such calls stay
  silently untyped (decisions 285, 286).
- Thumb: 9 of the 13 driver programs agree with x86-64 (last count).
- ABI: legalize splits a soft `f64` by `Rules::fits`; `Rules` should be declared in `lang` and
  generated; no target check yet that the convention's word matches `pointer_bits`.
- Backtraces: no call line per frame (native marks each call's origin; C cannot say where a
  call returns); no macOS (compact unwind, PAC). WASI reports the site only.
- Mach-O arm64 thread-locals are checked by linking with `ld64.lld`, never run on a Mac.
- A new project still writes a whole new shared memo file (~450 ms dev, after the build): memos
  whose keys name the project's functions but read shared inputs alone count as shared.
- Truly cold (empty store), threads wait ~1.1 s on the same `std` claims, once per toolchain.

## Next steps, most useful first

0. Editor integration (the owner's current focus; editors: Zed, Helix, VS Code, Neovim). The
   owner chose: the parser reads the grammar's tables rather than stating the same facts in code,
   and every source must agree with tree-sitter (192 of 198 now). In order:
   (a) the six files left (`cargo xtask tree-sitter` lists them): `std/os/libc.vun`
   (`[system.words]system.Word`: an element starting with a name continued by a member, which the
   `.starting` variants miss), three assembly files (a bound value inside an operand expression,
   `[{in a} + 3]`: bound, memory and label are operands only under an instruction, a context the
   grammar cannot yet say), `asm_thumb.vun` (`vcvt.s32.f32 s0, s1`), `syntax/patterns.vun`
   (`.none` after a `for` statement read as a member of it);
   (b) the parser reads the tables it restates in code: `precedence` (its nesting in `expr.rs`),
   `unterminated` and `transparent` (`block_like_at`), `admits`/`holds` (its list contexts),
   `line_ends` (`line_ends_before`), `literal_types`/`element_types` (read already), `preferred`
   (its choice of kind after the children); then the engine over the productions (the handoff's
   former step d), diffed against the hand parser on every file and by fuzzing;
   (c) publish `tree-sitter-vun` (the owner chose a repository of its own for the 8 MiB
   `parser.c`): an xtask task copying `grammar.js`, `conflicts.json`, `src/` and the queries and
   pushing; the editor packages point at it by `main` (Zed and Helix may need a commit hash:
   have the task record it and `cargo gen` read it);
   (d) try the packages in each editor (nothing was run in an editor yet; the Zed extension
   passes `cargo check`); then LSP: completion and signature help, references, rename, code
   actions from diagnostic fixes, inlay hints.
