## Front end: lexer, parser engine, CST/syntax, HIR, desugar, grammar and primitives tables

- [P1] HIR lowering hard-codes three `lang` names as string literals and builds a path from them, bypassing the generated `Item` table that already declares them - `compiler/front/hir/src/lower/implementation.rs:22-25`, used at `:90`, `:108`, `:113-116`
  Evidence: `const LANG: &str = "lang"; const IMPL: &str = "impl"; const TYPE: &str = "type";` and `fn lang(&mut self, name: &str, head: OriginId) -> ExprId { let object = self.synthesized_at(ExprKind::Name(Symbol::intern(LANG)), head); ... Name::Plain(Symbol::intern(name)) }`, called as `self.lang(IMPL, head)` and `self.lang(TYPE, head)`. The very same names are declared once in `lib/lang/lang/lang.vun:6` (`type: type = _;`) and `:84` (`impl: ($witness: type) -> Attribute(...) = _;`) and already have generated handles: `compiler/lang/items/src/lang/root.rs:71` (`pub const r#type: Item = Item::new(&["lang","type"]);`) and `:114` (`pub const r#impl`). The file's own header and `desugar.vun`'s header state the opposite rule ("so no `lang` name is written in the compiler"), and `vun-desugar` already carries `Item`-valued tables (`compiler/front/desugar/src/generated/markers.rs`, `MARKERS[0].item = vun_items::lang::safety::r#unsafe`), read from paths in `desugar.vun`.
  Why: renaming or moving `lang.impl`/`lang.type` in `lib/lang` (a normal language change) silently breaks every `impl` witness lowering: the synthesized `lang.impl(...)` call and its `-> lang.type` return would name a path that no longer exists, with no generated table or test tying the two together. It is exactly the "names built or matched as text" case the design rules forbid.
  Fix: add a table to `lib/lang/lang/syntax/desugar.vun` naming `lang.impl` and `lang.type` as `Item` paths (the shape `markers`/`form` already use), let `cargo gen` emit it into `vun-desugar`, and replace `LANG`/`IMPL`/`TYPE` + `Symbol::intern` in `implementation.rs` with that table; that removes the class (no `lang` name is written in the compiler, and the generator resolves the path).

- [P2] The assignment-token set is declared twice, independently, in tables with different owners; an unlisted compound operator compiles as a plain assignment with no diagnostic - `lib/lang/lang/syntax/grammar.vun:196` (`assign`) and `lib/lang/lang/syntax/desugar.vun:186` (`compound`)
  Evidence: `assign` lists `eq` plus all 16 `*=`, `+%=`, `*|=` … tokens (parser side); `compound` lists the same 16 tokens (minus `eq`) with their `op`/`narrowing` (desugar side). The consumer treats "not in `compound`" as "plain `=`": `compiler/mid/mir/src/build/assign.rs:32` `let Some(narrowing) = COMPOUND.iter().find(|row| row.token == op).map(|row| row.narrowing) else { let value = self.operand(value)?; self.assign(target, Rvalue::Use(value), origin); return Ok(()); };` (`sema/typeck/src/block.rs:46` has the same lookup pattern).
  Why: today the two lists agree, so nothing miscompiles. The moment a `x op= y` token is added to `assign` (or removed from `compound`) a parser-accepted `x *= y` becomes `x = y` at MIR with no diagnostic anywhere — silently wrong output from valid source.
  Fix: one source of truth for the set. Either assert in a test (or in the `xtask` generator) that `Assign::tokens == {Eq} ∪ COMPOUND.tokens`, or derive `compound`'s tokens from `assign` so the two cannot drift. The fallback in `assign.rs` should then be only for `Eq`.

- [P2] A tuple-index name whose literal does not fit `u32` silently lowers to the wildcard `Name::Hole` instead of an error - `compiler/front/hir/src/lower/mod.rs:184-186`
  Evidence: `NodeKind::Int => vun_syntax::literal::integer(self.text(n)).and_then(|i| u32::try_from(&i).ok()).map_or(Name::Hole, Name::Index),`
  Why: `t.4294967296` (a lexically valid `Int` in a member-name position; `member_names` admits `.int`) is lowered to `Name::Hole`, i.e. the `_` position, with no diagnostic — `map_or` conflates "the literal did not parse" (which the lexer already reported) with "the index is out of range" (which nothing reports). The reader sees a valid program whose member index became a hole.
  Fix: keep the two cases apart and report the out-of-range one (a `vun-diag` error naming the limit), or lower it to an `Error` name so later stages report it; only the already-reported malformed-literal case should fall back to `Hole`.

- [P2] A stale doc comment describing a removed `text` helper sits on `fn offset` - `compiler/front/syntax/src/lexer/mod.rs:98-101`
  Evidence: `/// The text a string, raw string, raw line or character token denotes; `None` for other tokens / /// and for malformed literals, which the lexer reported.` immediately above `fn offset(pos: usize) -> u32 { u32::try_from(pos).expect(...) }`. That description belongs to the string-decoding API now in `lexer/value.rs` (`bytes`, `literal`, `located`), not to a byte-offset cast.
  Why: the doc states a contract `offset` does not have, so `cargo doc`/readers are misled about a function the lexer calls per lexeme; it is a leftover from a moved/renamed function and hides which module owns that fact.
  Fix: delete the two lines (or move them onto the `value::*` entry point they describe).

## Open questions

1. `implementation.rs`: is writing `lang`/`impl`/`type` as literals intentional (e.g. a deliberate early-bootstrap exception), or an oversight the `desugar.vun` `markers`/`forms` pattern should cover? The generated `vun_items::lang::{r#impl,r#type}` handles suggest the latter.
2. `grammar.vun`'s `assign` and `desugar.vun`'s `compound` are two tables for one fact. Should the generator assert their consistency, or is `compound` meant to be derived from `assign`?
3. `lower/mod.rs::name` maps an out-of-`u32` tuple index to `Name::Hole`. Is there a spec rule for the index range, or should resolution report it (and with which error id)?
4. `lower/members.rs::variants` lowers variant payload args with `self.expr(a)` while `lower/exprs.rs::args` handles `FieldInit` (`admits` lists `.variants`). Is `.Variant(.x = T)` meant to be accepted, and if so should it not become a silent `ExprKind::Error`?
5. `Lit::Float(String)` carries the literal text to `Binary::parse` later. Is that the intended boundary, or should the HIR hold a parsed value?
