## Packaging and the Vun-side surface (packages, lang/std, corpus, generated handles)

I verified the generated handle and primitive plumbing, the lang desugar tables, the std algorithms most prone to wrong results (UTF-8, LEB128, CRC-32, big-int, float parse/format, calendar), and the manifest reader. Most of it is disciplined and single-sourced; the two concrete defects I can prove are docs/prelude drift.

- [P2] The default prelude re-exports `lang.impl` but not `lang.derive`, so the spelling documented for the derive attribute (`#[derive(f)]`) cannot resolve for any package on the default prelude; every real use is qualified `#[lang.derive(...)]` - lib/std/std/prelude.vun:10 (list `... impl, kind, ...`), lib/lang/lang.vun:85, lib/lang/lang/ops.vun:117
  Evidence: `lang.vun:85` documents ``/// `#[derive(f)]` on an interface ...`` next to `lang.vun:82` ``/// `#[impl(I(T))]` ...``; the prelude at `prelude.vun:10` exports `impl` but the `..lang.{ ... }` list has no `derive`; the only uses in the tree are `#[lang.derive(derive_eq)]` (`ops.vun:117`), `#[lang.derive(derive_hash)]` (`std/std/hash.vun:14`), `#[lang.derive(derive_debug)]` (`std/std/fmt/debug.vun:8`), `#[lang.derive(derive)]` (`std/std/fmt/json.vun:11`).
  Why: a person following the spec entry writes `#[derive(lang.ops.derive_eq)]` and gets `names.unresolved` for `derive` (it is only in scope as `lang.derive`), while the sibling attribute `impl` written bare does resolve - the two documented forms disagree with the declarations.
  Fix: add `derive` to the `..lang.{ ... }` list in `lib/std/std/prelude.vun`, or correct `lib/lang/lang.vun:85` to `#[lang.derive(f)]`; either way make the doc and the prelude agree.

- [P2] `exponent_cap` is declared with a doc that promises clamping, but no code reads it - lib/std/std/float/parse.vun:19
  Evidence: repo-wide, the only occurrences are the declaration `exponent_cap: std.math.Exponent = 2200;` and its generated handle `compiler/lang/items/src/std/float_/float_parse.rs:14`; the doc says "An exponent past this is the same as this: the number is far past what any float holds", yet `scan` (parse.vun:60-107) only bounds `magnitude < 100_000` and lets `out.exponent: i64` grow, and `round` (parse.vun:120-140) rules out far exponents with the `size > High` / `size < Low` tests, never with `exponent_cap`.
  Why: the constant advertises a clamp that no path performs; a reader trusting it (or a future edit that assumes exponents are already capped) is misled, and the named constant is dead weight.
  Fix: either delete `exponent_cap` (and its doc), or use it as the intended cap in `scan`/`round`; the current `$High`/`$Low` bounds already give the correct result, so deleting is the smaller change.

## Checked, clean

- Generated handles vs sources: `compiler/lang/items/src/{lang,std,targets}/**` are one module per namespace/member, filtered only by the `_` private prefix in `compiler/tools/generate/src/items.rs`; the sample paths agree with `lib` (`items/src/tests.rs` asserts `std.build.Build.new`, `std.build.Action.dep`, `lang.target.Endian.little`). `lang/primitives/src/generated/*` mirrors exactly the `= _` declarations of `lib/lang`, and `Primitive::at`/`namespace`/`item` are consistent (`primitives/src/tests.rs`).
- Primitive coverage: `tools/driver/tests/driver/primitives.rs` asserts every callable primitive is reached by a corpus/test program that lowers, and `low/lower/src/func/primitive.rs` lowers each runtime primitive or returns a structured `Unlowered::unsupported`. No `= _` primitive appears declared with no consumer.
- `lib/lang/lang/syntax/desugar.vun`: the operator/prefix/borrow/compound/marker tables are the single source of truth; `Comparison` has six variants matched by six `comparisons` rows, `compound` covers the 16 assignment tokens, `markers`/`fn_markers` line up with the `lang` attributes. No name is matched as text here, and the compiler reads these tables (matches `Primitive::Lang(...)` / `unlowered` form lookups), not hard-coded operator names.
- Integer semantics in `lib/lang/lang/int.vun` and its lowering: exact range arithmetic, `to`/`wrap`/`sat`/`fits`, shift/compare/div trap rules; `std/int.vun`'s `Narrow` is an interface whose `= _` are requirements (not compiler privilege), and its impls call the `lang.int` primitives - no std-side privilege.
- `std.os.vun`: `std.os.start` is a declaration (`runtime(lang.target.current).start`), not a hard-coded entry point; the `symbols` struct is the single source of the link symbol names, and `posix_error` maps the documented `errno`s to typed `Error`, falling back to `.number(n)` by design. The `runtimes` list is declared data.
- `compiler/pkg/build/src/manifest/mod.rs`: every required field is read and unknown fields diagnosed; `field::PACKAGE`/`DEP`/`REPLACEMENT` are one list each, matching the `Manifest`/`Dep`/`Replacement` structs; `Version::parse` (base/span/src/key.rs) rejects non-canonical and non-digit parts.
- Hand-written std algorithms I traced for wrong results found no defect: `text/utf8.vun` decode/encode (overlong, surrogate, >10FFFF, lead-byte ranges all rejected), `codec/varint.vun` (`longest`/shift-63 overflow guard, zigzag), `hash/crc32.vun`, `math/big.vun` (`shl`/`shr` carry and `lost` handling, `div_small`, `sub` borrow), `float/parse.vun` round/assemble, `fmt/float.vun` `fixed` (tie-to-even, `309+380 < 700` digit bound avoids the `at` underflow), `seq/sort.vun` heapsort/binary-search, `time/date.vun` Hinnant civil-date round trips and weekday offset (1970-01-01 = Thursday).
- Corpus: `tools/xtask/src/corpus.rs` treats `corpus/planned` files that still report only `NAMES_UNRESOLVED`/`TYPES_NO_MEMBER` as pending and fails loud when one goes clean, so a blocked planned program is reported, not hidden.
- No `TODO`/`FIXME`/`unimplemented!`/`todo!` anywhere in `compiler/**` or `lib/**`; `unsafe` in the reviewed Vun surface is confined to `std.mem`/`std.os` primitives as declared.

Note on method: I reviewed by reading; I could not run `cargo xtask lines`/`cargo nextest` (no shell in this session), so file-length and test-suite cleanliness are taken from `docs/HANDOFF.md` rather than re-run.

## Open questions

1. Is `#[derive(f)]` intended to be usable bare (i.e. should `derive` be prelude-exported like `impl`), or should the `lang.vun` docs say `#[lang.derive(f)]`? The two attribute docs disagree today.
2. Was `lib/std/std/float/parse.vun`'s `exponent_cap` meant to cap `scan`'s exponent, or is it a leftover from an earlier design?
3. `std.time.date.parse` accepts a bare `2024-02-29T12:30:45` with no `Z`/offset (parse.vun in `time/date.vun`, the `at != text.len()` path with `offset = 0`), while its doc says the text ends with `Z` or an offset. Is that leniency intended?
4. The default prelude `..lang.{ ... }` is a hand list; should it be derived from a declaration in `lib/lang` (e.g. a `prelude` table) so it cannot drift from the `lang` surface?
