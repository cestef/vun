## Target instruction descriptions (compiler/isa/*) and their encodings

- [P1] x86-64's operand fit accepts memory the x86-64 assembler cannot encode, so `Blocks::fit` promises more than it delivers (arm64/thumb check this, x86-64 does not) - compiler/isa/x86_64/src/fit.rs:63-85 vs compiler/isa/arm64/src/fit.rs:110-112 and compiler/isa/thumb/src/fit.rs:107-109
  Evidence: arm64 and thumb call `Arm64::addressable(mem, self)` / `Thumb::addressable(mem, self)` inside `Kind::fits`; x86-64's `Kind::fits` instead maps every memory to a canonical register operand and never consults `addressable`:
  `Given::Mem { writeback: Writeback::No, .. } => { Operand::Mem(Mem { base: Base::Reg(Reg::Rax), disp: 0 }) }` (compiler/isa/x86_64/src/fit.rs:74-76). x86-64 memory *can* carry an index (`mem(rax, scaled(rcx, 8), 16)` is parsed, compiler/sema/asm/src/x86_64.rs:52-66).
  Why: a block writing indexed/absolute/symbol-off-register memory (`[rbx + rcx*4]`, `[0x1000]`) fits, so `Blocks::fit` (what sema and `vun check` use) accepts it, while `X86_64::addressable` (compiler/isa/x86_64/src/inline.rs:103-112) rejects `Indexed`/`Absolute`/`SymbolOffRegister`. The program is reported only later, from a backend (`A::addressing` in compiler/native/core/src/inline/block.rs:35, compiler/back/c/src/emit/func/asm/mod.rs:64), so `vun check` says OK and `vun build` fails on the same source. The doc on `Blocks::fit` ("A form checked so is one the assembler encodes, by the same predicates", compiler/isa/api/src/blocks.rs:66-71) is false for x86-64.
  Fix: in `Kind::fits`, for `Given::Mem { writeback: Writeback::No, mem, .. }`, call `X86_64::addressable(mem, self).map_err(|_| Why::Kind)?` before substituting the canonical operand (the same shape arm64 uses); `operand` in inline.rs already panics on the shapes this rejects, so the check must precede it.

- [P2] Arm64's `Form` cannot express "these two registers must differ", so `ldp`/`stp` accept the same register twice, which the manual calls UNPREDICTABLE - lib/lang/lang/arch/arm64.vun:175-190 (Form declaration), lib/lang/lang/arch/arm64/memory.vun:106-137 (ldp/stp); machinery already present at compiler/isa/api/src/word.rs:99-101,178
  Evidence: `vun_isa::word::Form` has `pub apart: &'static [[u8; 2]]` and `Form::encode` rejects a pair that names one register (`if self.apart.iter().any(|&[a, b]| named(a).is_some() && named(a) == named(b)) { return None; }`), and thumb uses it (`apart: &[[2]u8] = &[]` in lib/lang/lang/arch/thumb.vun:192, set as `.apart = &[[0,1]]` on `ldrd`, `.apart = _pair_back` on `ldr` writeback forms, etc., lib/lang/lang/arch/thumb/memory.vun:58-167). Arm64's `Form` struct has no such field and no arm64 `.vun` ever sets one, so every generated arm64 form carries `apart: &[]` (arm64 forms always use `word::Form::new`, e.g. compiler/isa/arm64/src/generated/forms_0/ldp.rs:4-31).
  Why: `ldp x0, x0, [x1]` / `stp x0, x0, [x1]` fit and encode silently; the Arm manual makes Rt == Rt2 UNPREDICTABLE, and the same shape is a hard error the Thumb table already encodes for `ldrd`/`strd`. Any other same-register restriction (e.g. an atomic pair) has no way to be declared on arm64.
  Fix: declare `apart: &[[2]u8] = &[]` on arm64's `Form` (mirroring thumb.vun) and set `[[0,1]]` on the `ldp`/`stp` pair forms in lib/lang/lang/arch/arm64/memory.vun.

- [P2] The doc for `Registered::uses` is the doc written for `Registered::operand`, which is left undocumented - compiler/isa/api/src/blocks.rs:114-137
  Evidence: the block above `fn uses` reads "A block's operand at a position of `kind` … # Panics … Panics on memory the assembler does not address ([`Registered::addressable`]). The bindings of `block`, in the order `Block::bindings` gives them, each with the kind of the position it is at." while the later `fn operand` (blocks.rs:200-204) has no comment at all. Only `uses` carries `#[must_use]`.
  Why: the trait's contract for `operand` (where `place` is used, what panics) is attached to the wrong method; a reader of the API is told `uses` panics on memory it does not address, which is not what it does.
  Fix: move the comment to `fn operand` and give `uses` its own one-line doc ("The bindings of `block`, in the order `Block::bindings` gives them, each with the kind of the position it is at.").

## Open questions

- Given::operand in compiler/isa/api/src/fit.rs:88-90 turns a float immediate into `Operand::Imm(i64::from_ne_bytes(float.double.to_ne_bytes()))`, taking the *double* bits at every width even though `FloatBits::at(width)` exists for that purpose (compiler/isa/api/src/fit.rs:106-112) and wasm32 uses it (compiler/isa/wasm32/src/fit.rs:115). Today only `Imm::Zero` is reachable from a float literal (arm64/fp.vun:21, thumb/fp.vun:94), so no 32-bit float is mis-encoded. Is a 32-bit float immediate expected to be added, and should this use `at(size)`?
- Arm64 LDP/STP: are the same-register and writeback-alias cases (UNPREDICTABLE) meant to be rejected at all, or does the design accept "the assembler would still assemble it"?
- x86-64 memory shapes: is the deferred `addressable` check intentional (so the fit stays operand-shape free), or should `fit` match arm64/thumb and report it during checking?
- `Processor` stores features in a `u64` bitmask indexed by `F::ALL` position (`compiler/isa/api/src/need.rs:76-78,171-173`); is there a check that no instruction set declares more than 64 features?
- Thumb's `Cc::not()` panics on `al` by design (compiler/isa/thumb/src/reg.rs:128-133) and is called from native/thumb/src/isel/term.rs:42 and asm/thumb/src/tests/mod.rs:55; can an `al` condition reach those call sites?
