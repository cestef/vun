# Trying Vun as a new user (2026-10-01)

A session playing someone who has just found the repository: follow the README, then write a small
real program. The program is `corpus/accept/programs/bf`, a Brainfuck interpreter. Everything ran
on a fresh copy of the repository at `aac540e0` on an x86_64 Fedora machine.

Verdict: Vun works end to end. The README's tour runs, and a package with a parser, an
interpreter, a command line, unit tests and a property test builds, tests and fuzzes. The problems
are one form that checks clean and then fails to build, two command-line traps, and a crash under
WASI.

## The project

`bf` is a package of four files:

| File | Holds |
|------|-------|
| `build.vun` | the manifest, written by hand since there is no `vun new` |
| `bf.vun` | `Program.parse` (brackets matched with a stack), `Program.run` (30000 wrapping cells, output through any `std.fmt.Writer`), a `Format` impl for its errors |
| `bf/app.vun` | the command line: reads the file named by its argument and standard input, reports usage and read errors |
| `bf/tests.vun` | six unit tests and a property test over any `&[u8]`, on a buffer `Sink` written for them |

`examples/` holds `hello.bf`, `cat.bf`, `busy.bf` (about 33M instructions) and `broken.bf` (an
unmatched `[`).

Results:

- All 7 tests pass; `vun fuzz` ran 10000 cases of the property with no trap.
- Hello World and `cat` run natively, with the native backend, and under qemu for
  `linux.arm64.kernel`.
- `busy.bf` runs in 139 ms in a debug build and 80 ms with `--release`.

## Bugs, worst first

1. `vun check` passes a form that the build then rejects as a compiler bug. `a[..n]` checks
   clean, then `vun run` fails with `backend.unlowered: typing gave this Index no type and reported
   nothing`. `a[0..n]` and `a[n..]` work. Prefix `..` is a spread, not a range (spec 01, section
   2), so the form is invalid, but typing should say so, with a hint to write `0..n`. A Rust user
   writes `[..n]` within minutes. The message also names the form `Index`, which reads as the
   user's own type when they have one by that name (as `bf` does).

   ```vun
   start := std.os.start(main);
   f := (s: &[u8]) -> usize { s.len() };
   main := (sys: &mut std.os.System) -> std.os.Exit {
       a: [8]u8 = [0; 8];
       n: usize = 3;
       std.fmt.print(&mut sys.stdout(), "{}\n", f(&a[..n]));
       .ok
   };
   ```

2. A stack overflow under WASI is a raw memory fault. A 200 KB local runs natively; built for
   `wasi.wasm32.p1`, wasmtime reports `memory fault at wasm address 0xfffaa040 in linear memory of
   size 0x20000`. There is no stack check and no trap report. `bf/app.vun` fails the same way,
   with two 64 KiB buffers in `main`.

   ```vun
   start := std.os.start(main);
   main := (sys: &mut std.os.System) -> std.os.Exit {
       mut big: [200000]u8 = [0; 200000];
       big[199999] = 7;
       std.fmt.print(&mut sys.stdout(), "{}\n", big[199999]);
       .ok
   };
   ```

3. `vun run -- file` compiles `file`. The optional `[path]` takes the first word after `--`,
   so `vun run -- examples/hello.bf` parsed the Brainfuck file as Vun source and reported four
   syntax errors. Spec 12, section 7 says words after `--` go to the program. `vun test <name>` has
   the same trap (`test.no_namespace`). Both work only with the path written: `vun run . --
   examples/hello.bf`, `vun test . <name>`.

4. `vun test -q` prints nothing when a test traps. It exits 1 with no output. `-q` keeps
   "results and diagnostics", and a trapped test is a result.

5. `std.panic.fail(..);` does not make its block diverge. `.err(_) => {
   std.panic.fail(.message("..")); }` is typed `()`, though `fail` returns `lang.never`, while a
   block ending in `return x;` diverges. Without the braces and `;` it works.

6. `std.lints.naming.case` denies an interface's type member bound to `()`. In an impl of
   `std.fmt.Writer`, `Error := ();` is reported at `deny` with the fix "rename it `error`", which
   would break the impl: the interface requires a member named `Error`, and `()` is a type there.
   `bf` names its own error type (`Full`) to avoid it.

7. `vun test` and `vun build` do not show a lint that `vun check` denies. With the lint above,
   `vun check` failed with one error while `vun test` built and passed the package; the corpus run
   caught it.

## Diagnostics

- A wrong fix. Slicing a borrow gives a borrow, so `read(&mut into[n..])` with
  `into: &mut [u8]` is `&mut &mut [u8]`. The help proposes adding `.*`, marked `[unsafe]`; the fix
  is to drop `&mut`.
- Alias names are lost. `u8` is shown as `Int(0..=255)` everywhere, and `int.does_not_fit`
  notes "`Int(0..=4095)` is `Int(0..=4095)`" where it could name the declared `Index`.
- No hint that a mutable place does not narrow. After `if p.len == capacity { return ...; }`,
  `p.len` keeps its range because it is mutable (spec 04, rule 4). The help could say to bind it
  first, which is the fix.
- A missing `Format` impl is reported inside std. Printing an enum without one points at
  `lib/std/std/fmt.vun:125` with the user's call as a note, and says "no member `format` in
  `Error`" without saying which `Error` (`std.os.Error` or the user's).
- The report of a trapped test is noisy. The assertion is printed twice, 9 of its 11 frames
  are the runner's and std's, and the operands' values are not shown.

## Missing pieces a new user meets

- No guide. The documentation is the specification and the compiler's internals; the
  language was learned from `docs/spec/` and the sources of `lib/std`.
- No `vun new` or `vun init`, while spec 12 says the package `.id` is "generated by
  `vun new`". The id has to be invented.
- Empty modules of std. `std.collections` and `std.text` hold only their doc comments. There
  is no `Writer` over a buffer, no reader interface (input is `Stream.read` alone), and no `==` on
  structs or enums without hand-written `lang.ops.Eq` impls, so a test cannot compare
  `parse(..) == .err(..)`.
- Output names. The executable is named after the root file (`app`), and `std.build.Options`
  has no field for its name. A test run reports `Building build.vun` and `Running
  .vun/build/build`.
- `vun fmt` does not take a path as the other commands do. With no argument it does nothing
  and exits 0; `vun fmt .` fails with `io.unreadable_file` ("Is a directory").
- The spec is ahead of the command line or behind it:
  - `vun check --traps` and `--widen` (spec 04, section 1) do not exist.
  - Spec 12, section 7 lists `test` and `fix` in the table of commands and again among those
    still to come.
  - `--backend` offers `cranelift`, `qbe` and `llvm`, which only report that they cannot
    generate code yet.

## Smaller things

- The example of `vun explain int.does_not_fit` shows the corpus annotation `//~ int.does_not_fit`.
- An untracked work directory, `lib/std/std/lints/.vun/queries`, was left inside std by an earlier
  run.
- The path of a program run in the current directory prints as `././.vun/build/app`.
- `cargo run -q` in the README silences cargo but not vun's status lines.

## What worked well

- The tour ran on the first try, after a cold build of 68 s.
- Range integers found a real off-by-one in the parser at compile time.
- Property tests and `vun fuzz` needed no setup.
- `vun doc`, `vun explain`, `vun target list` and `vun toolchain show` are clear, and running a
  program for another architecture through qemu needed nothing.
