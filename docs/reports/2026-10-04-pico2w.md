# Trying Vun on a Pico 2 W (2026-10-04)

A session playing someone who has the toolchain and a Raspberry Pi Pico 2 W (RP2350, Cortex-M33)
on USB, and wants a program running on it. Checkout at `e37b10a6` on x86_64 Fedora, `vun` built
from it with `cargo xtask install --profile release`.

Verdict: **a Vun program now runs on the board, but only because a board package was written
first.** The repository has no RP2350 support, the bare-metal path needs a GNU toolchain, and a
board without a console gives no sign of what a failed boot did. Bringing the chip up took about ten
power cycles, most of them from one wrong address in the boot ROM, which Vun could not tell me
about.

## What ran

`lib/boards/rp2350` (new, 4 files, uncommitted) follows the stm32f4 board: a runtime (vector table,
reset handler, critical sections), the IMAGE_DEF block the RP2350 boot ROM needs, the memory
layout, a GPIO output and the ROM's `reboot`. The firmware that finally ran:

```vun
start := rp2350.start(.{ .main = main, .trap = rp2350.halt, .interrupts = .{} });

mut loaded: u32 = 0x1111_0000;
mut zeroed: u32 = 0;

main := (p: rp2350.Peripherals) -> never {
    mut led := p.gpio.pin(15).output();
    led.high();
    led.toggle();
    led.toggle();
    unsafe { zeroed +%= 0x42; }
    ok := unsafe { loaded == 0x1111_0000 and zeroed == 0x42 };
    if ok { rp2350.rom.bootsel() }
    for {}
};
```

Built with a plan (`b.program` with `rp2350.layout.memory` and `.sections`, target
`bare.thumbv7em.eabihf`), loaded with `picotool load -x -t elf`. It booted from flash, `.data`
was copied and `.bss` zeroed (the program only reboots if both hold), the ROM call worked and the
board came back in BOOTSEL.

Not checked: the level of GP15 (the Pico 2 W has no LED on a GPIO, so nothing was attached),
interrupts, timers, floating point, `--release`, the RISC-V cores.

The board's original 4 MiB flash was saved to `~/pico2w-original-flash.bin` before the first load.

## Bugs, worst first

1. **`vun build --library static --target <t> file.vun` ignores the target.** Both `--target` and
   `VUN_TARGET` are dropped on this path: the archive holds an x86-64 object, and the linker for
   the real target reports `file format not recognized` far from the cause. The same library built
   by a plan (`b.program(.{ .output = .static, .target = .. })`) is correct.

2. **Silent hang on a bad address, and on any fault.** Calling the wrong ROM routine hard-faulted,
   and the board's fault vectors are all `unhandled`, a spin. Nothing is reported by the runtime,
   by `picotool`, or by the host, so every wrong guess looked like "the program does not run".
   The stm32f4 board has the same shape. A board with no console needs a way to say what it hit:
   a fault handler that records the fault registers somewhere a later boot can read, or a
   documented debug route.

3. **`vun --version` cannot tell builds apart.** A stale `~/.cargo/bin/vun` from two days earlier
   and the fresh toolchain both print `vun 0.1.0`, and the stale one came first on `PATH`.
   `cargo xtask install` installed to `~/.local/bin` without noticing the shadowing copy.
   `vun toolchain show` did name the library path ("the checkout it was built from"), which is how
   it was found.

4. **`backend.lacks` for inline assembly points at the board.** Building a bare-metal program
   with `--backend native --linker lld` fails with ``backend `native` cannot express inline
   assembly`` at the `wfi()` in the board's runtime. The fix for the user is "use the `c` backend
   and install `arm-none-eabi-gcc`", which `vun target list` does say ("lacks arm-none-eabi-gcc")
   but the error does not.

5. **`int.does_not_fit` names the wrong thing.** `ptr.offset(slot)` with `slot: usize` on a
   32-bit target reports "this is `u32`" against `i32`: `usize` is shown as `u32` and the
   parameter's declaration is not pointed at. The fix is to declare `slot: i32`.

6. **`vun check <board dir>` checks for the host.** A board declares its `target`, but checking
   the package uses the host's, where `usize` is 64 bits: address arithmetic that is right for
   the chip fails with `Int(0..=2^65 - 2)` does not fit `u64`, and passes with `--target`.

## Missing pieces a firmware user meets

- **No RP2350 board.** `lib/boards/rp2040` is a one-line stub, there is no `rp2350`, and no target
  for the Cortex-M33 (`thumbv8m.main`) or the Hazard3 cores. `bare.thumbv7em.eabihf` runs on the M33
  because Armv8-M mainline is a superset, but it is the M4F's FPv4 profile, and the runtime never
  enables the FPU (`CPACR`), so the first float instruction would fault. The new board is not in
  the generated items (`cargo gen` not run), the docs, or `HANDOFF.md`.
- **No flashing.** `b.flash` takes a probe. There is no BOOTSEL route, no UF2 output, and the
  executable has no extension (`.vun/build/fw`), so `picotool` refuses it until given `-t elf`.
  `picotool` itself had to be run by hand, with a hand-held BOOTSEL button each time the program
  hung.
- **No output from a running board.** No UART, no USB serial, no semihosting over a probe (the
  stm32f4 board has semihosting for qemu only), no timers or ticks. The only observable results
  were "the board came back" and values read through an SDK harness.
- **Pico 2 W specifics.** The LED is behind the CYW43 radio, which needs its firmware and a PIO
  SPI driver, so there is no blinky without hardware attached.
- **Hand-written boot details.** The IMAGE_DEF block (5 words), the vector table size (67) and
  the ROM function table are all typed by hand from the datasheet. No generator or table in `lib`
  holds them.
- **Debuggability of the output.** The ELF names functions `f1`, `f20` and variables `d0`, so
  `nm`, `objdump` and a debugger show no source names. A debug build keeps a frame pointer and a
  copy of every argument on the stack; the 16-line program above is a 10 KB image.
- **No way to find a primitive.** `lang.mem.function_at` (a function from an address) is the one
  piece of API this port needed; it was found by searching `decisions.md` (entry 416), not by
  `vun doc` or the spec. `vun doc` was not tried.
- **Friction in the type system.** An enum has no conversion to an integer, so a table index is a
  `match` (the stm32f4 board does the same). A private field (`_n`) cannot be set by a sibling
  type of the same module, so each such type needs an `of` constructor.

## How the bring-up went

Eight designs, in order. Six hung (the board did not return to BOOTSEL), and in each the cause was
the ROM lookup address; two loads of mine were also wasted on stale binaries, see below.

| # | Image | Result |
|---|-------|--------|
| 1 | blinky-style: GPIO, signature in SRAM, ROM reboot | hung |
| 2 | same, plus the tick generators started | hung |
| 3 | minimal chain of reboot attempts with markers in SRAM | hung |
| 4 | SDK program calling `reset_usb_boot` (control) | returned |
| 5 | Vun `main` doing only the ROM reboot | hung |
| 6 | SDK app with USB serial, Vun linked in as a library, printing what Vun computed | showed the bug |
| 7 | the same, offset `0x7df8` | hung |
| 8 | offset `0x16`, then the final firmware | returned both times |

The wrong address: the ROM keeps the pointer to `rom_table_lookup` at `0x18` on the RP2040, at
`0x16` on RP2350 Arm, and below the entry at `0x7dfc` on RP2350 RISC-V. The first value came from
memory, the second from misreading the SDK's `#if` nesting (`bootrom_constants.h`). The call
sequence itself (code `'R','B'`, flags, `delay_ms`) matched the SDK byte for byte and was never
the problem; the disassembly (`arm-none-eabi-objdump`) confirmed it at every step.

What found it: a control from the pico-sdk (step 4) proved the board, cable and ROM were fine; then
a static library built from Vun, linked into an SDK app with USB serial, printed `vun reboot=0x7d24
sdk reboot=0x571` for the same lookup. Two lessons for the port: (a) read one of the board's own
registers or a ROM value back before trusting a call, and (b) after a ROM reboot, SRAM is not a
mailbox, since reads of `0x20070000` came back zero.

Two mistakes of mine cost a power cycle each and are not Vun's: loading a stale ELF after a failed
build, and loading a harness before rebuilding it with the fix. A build and a load belong in one
`&&` chain.

## Environment

- **Nix could not build or fetch.** `nix shell nixpkgs#gcc-arm-embedded` failed with `opening lock
  file ... Permission denied`. The store is `root:nixbld` with the daemon disabled, and the
  daemon's socket was refused by SELinux: `/nix` is labelled `default_t`, so `init_t` cannot create
  the socket. Fixed with `semanage fcontext -a -t var_run_t '/nix/var/nix/daemon-socket(/.*)?'`,
  `restorecon`, and `systemctl start nix-daemon.socket` (not enabled at boot).
- **`picotool load -f` raced the reboot** once ("not responding") and worked on the retry;
  `picotool reboot -f -u` is the reliable form against an app with the SDK's reset interface.
- The pico-sdk, its `tinyusb` submodule and the datasheet text live in `~/code/strangers`.

## Suggested next steps

1. Fix `--library` so it honours the target (bug 1), with a test that builds a library for a
   non-host target and checks its object's machine.
2. Land `rp2350` properly: a `thumbv8m.main` target (FPU enabled at reset), the IMAGE_DEF block
   and vector table generated from declarations, a fault handler that leaves a record, then
   tick/timer, UART and a `.uf2` or BOOTSEL flash step in `std.build`.
3. Give bare boards one observable output before anything else: it is what turns a ten-cycle
   bring-up into a one-cycle one.
